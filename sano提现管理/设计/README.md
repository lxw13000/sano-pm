## 规格与组织

参考 `sano人员与直播管理` 的专项结构和视觉风格：1760×1120 桌面评审视口、深蓝导航、紫色主操作、浅色卡片。列表宽表内部横向滚动，订单和操作固定。初审／复审为右侧大抽屉，头尾固定，中间滚动；订单详情为左右分栏居中弹窗，左约 65%、右约 35%，独立滚动，无页签。

本专项采用 HTML/CSS/JavaScript 交互源文件，不额外输出 SVG。样式由基础 styles.css 与工作台调整 workbench.css 组织。源文件不依赖在线字体、CDN、npm 安装或网络请求，可直接编辑；PNG 来自同一交互源文件，避免静态图与交互规则脱节。

当前为 V1.4 提交二次确认版；V1.0 见归档。主列表全部字段直接展示，不提供隐藏或展开字段设置。本批订单列表在上、本次处理在下；提交位于处理块内，底部仅关闭，避免并排误操作。抽屉不提供二次筛选或勾选，处理参数作用于确定的本批。展开／收起在本次处理标题旁，核单提示红色加粗；提交后只保留一条动态结果摘要，参数展开只读。支持就地转复审和最近批次回看。初审、复审及退款都需二次确认，返回修改不执行，确认后才打款或退款。

示例数据固定在 2026-10-22 的业务背景，新增操作时间按 Asia/Shanghai 显示当前操作时间。12 笔示例覆盖六种状态。渠道与人名、账户、金额均为虚构；页面刷新重置数据，不持久保存。

## 推荐演示路径

### 1. 初审跨提现方式

1. 打开交互原型，点击“待审核”。
2. 勾选 GCASH 与 BANK 订单，点击“批量初审”。
3. 保持审核通过，提交；每笔按自身提现方式自动选择渠道，状态先为打款中。
4. 抽屉不关闭。约 8 秒后点击手动刷新，或等待 30 秒自动刷新，看到实际结果；本批订单不消失。
5. 另开“初审 · 驳回已退款”场景查看不通过结果。初审驳回原因沿用现有规则，本原型选填，不擅自新增用户可见要求。

### 2. 失败复审与循环

1. 点击“打款失败”，先勾选一笔 GCASH，BANK 将提前禁选，提示只可选择同方式；取消选择后可切换 BANK。也可先点击 GCASH 方式快捷筛选后当前页全选。
2. 只勾选三笔 GCASH，点击批量复审；它们历史渠道可以不同。新开复审的是否换号不预选，需明确选择。
3. 渠道选择 pay_roll、修改订单号选是，填写内部备注后提交。
4. 三笔订单分别换号、进入打款中；原型约 8 秒后提供两笔成功、一笔失败的模拟结果。
5. 手动刷新或等待自动刷新。原三笔始终保留；抽屉内没有二次筛选或勾选。
6. 点击“复审失败订单 1 笔”进入仅含失败单的新批，重新核对参数后明确提交；可返回原三笔完整结果。成功和打款中的订单不会重复处理。

“自动选择”会按该提现方式的配置优先级选渠道；选项仅包含配置且可用渠道。换号选否则编号保持不变。操作不会修改全局渠道配置。

### 3. 复审退款

1. 打开“复审 · 退款理由”场景。
2. 清空退款理由并提交，触发必填提示。
3. 填写理由后提交，订单显示“已退款”；理由用户可见，内部备注独立记录。
4. 渠道和修改订单号字段在退款时隐藏，不参与提交。

### 4. 详情与历史

1. 打开“订单详情 · 左右分栏”。左侧查看现有详情，右侧从发起开始查看事件。
2. 右侧顶部先看最新进展，可点击“跳到最新／回到发起”，查看三次复审换号、三次失败及第四次打款成功；左侧位置不变。
3. 单独滚动左侧查看收款资料和备注，其他空的收款／身份字段可展开；右侧位置不变。
4. 在抽屉中打开详情，关闭详情后回到原抽屉，保留草稿与本批订单。
5. 当前及历史订单号均可检索同一笔示例；编号有复制入口。

### 5. 部分提交未受理

“复审 · 部分提交未受理”场景展示两笔受理、一笔未受理；未受理项仍为打款失败，逐笔显示提交结果；通过“重新处理未受理订单 N 笔”进入下一固定子批次。不得把未受理显示为打款中或成功。

### 6. 初审失败就地转复审

打开“初审结果 · 就地转复审”，两笔成功一笔失败。点击按方式分组的“复审 GCASH”直接进入失败单复审；顶部可返回原初审批次，所有原批订单仍在，状态随实际结果更新。

### 7. 不占住抽屉等结果

任一批提交后手动关闭抽屉，可继续处理另一批；从列表“最近处理批次”回看先前结果。本原型只保留本次页面打开期间最近 10 批，刷新页面后清空。

### 8. 提交二次确认

新增四个确认场景：初审通过、初审驳回退款、复审通过（含渠道和是否换号）、复审退款（含用户可见理由）。点击“返回修改”或按 Escape，不改变任何订单；核对笔数／金额／处理参数后点击“确认提交”才执行。提交完成仅关闭确认弹窗，抽屉继续保留。

## 场景入口

场景由 `源文件/index.html?scene=场景ID` 打开，完整清单见 [scenes.json](生成工具/scenes.json)。入口场景使用同一套交互，均可继续操作；部分场景在打开时自动完成演示提交，以复现评审状态。

## 重新生成与验证

本机已存在的 Node、Playwright、Chrome、Sharp 用于 PNG 导出及验证；浏览器使用原型本身不需要这些依赖。

```powershell
node .\生成工具\validate-prototypes.js
node .\生成工具\render-prototypes.js
```

也可以使用 `生成工具/重新生成.ps1`。不同环境通过 `SANO_NODE_MODULES` 指定包含 Playwright 和 Sharp 的 node_modules 目录，`SANO_CHROME` 指定 Chrome 程序路径。脚本默认值沿用参考专项的本机运行时路径。

`validate-prototypes.js` 执行业务交互和布局验证并生成验证记录；`render-prototypes.js` 从同一源文件输出 25 张 PNG、总览及导航。导出时不展示短暂 toast，不改变业务状态。

## 原型边界

所有打款、退款、渠道回调和订单号生成均为浏览器本地模拟，不连接后台。默认提交后 8 秒产生演示结果，再经刷新展示；正式环境以服务端实际状态为准。生产中的资金账务、退款失败、并发操作、查询异常和渠道失效需依据需求文档实现，不能用本地模拟结果代替接口验收。
