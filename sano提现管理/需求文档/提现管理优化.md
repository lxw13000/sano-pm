# 管理端提现功能优化需求

版本：V1.4 · 提交二次确认  
日期：2026-10-22  
范围：提现列表、人工初审抽屉、失败复审抽屉、订单详情及历史时间轴。

## 1. 背景与目标

现状是所有提现订单均需人工审核，打款失败后通过多个独立按钮回退待审核、修改订单号或退款。优化后由程序按金额规则完成自动／人工分流，人工审核界面聚焦初审与失败复审，批量提交后持续查看本批订单的真实结果，并可追溯多次打款的生命周期。

本设计以本次沟通确认规则为准。附带的三张截图仅作为现有字段和界面参考，截图中的旧操作按钮不视为新增需求。

## 2. 范围与边界

1. 自动审核金额范围可全局配置，也可按国家＋提现方式配置。管理操作界面不提供该配置、不判断阈值，呈现的订单已由程序完成分流。
2. 自动审核通过或人工初审通过后，程序按订单提现方式配置的渠道优先级自动选择渠道并打款。
3. 打款失败即需要复审，不新增“待复审”订单状态，也不回退为“待审核”。
4. 复审指定渠道只作用于本次选择的订单，不修改提现方式的全局配置和优先级。
5. 本次未重新设计渠道配置页、金额配置页、手续费／汇率算法、权限系统或真实支付接口。现有导出可沿用；强制成功等其他既有能力是否保留，按现有业务独立评估，本原型不模拟强制成功。

## 3. 术语

| 名称 | 含义 |
| --- | --- |
| 提现方式 | 用户选择的收款方式，如 GCASH、BANK；决定可使用的渠道配置 |
| 提现渠道 | 实际执行打款的渠道，如 payer_max、pay_roll |
| 初审 | 对“待审核”订单进行人工审核 |
| 复审 | 对“打款失败”订单选择退款或继续打款 |
| 修改订单号 | 提交是／否；选“是”后后台自动为本次提交的每一笔订单分别修改订单号，不由运营手动填写 |
| 上游订单号 | 渠道侧返回的标识；与“是否修改订单号”区分展示，实际命名按现有后台字段映射 |
| 本批订单 | 打开抽屉时选中的完整订单集合；提交后状态变化也不从抽屉中移除 |

修改订单号是为了适配“订单号一旦使用，不论成功或失败均不可再次使用”的渠道。多次编号变化仍需关联同一笔提现生命周期，保留修改前后值；本文件不限定后台主键实现。

## 4. 订单状态与流转

订单状态严格为以下六种：

| 状态 | 含义 | 当前允许的本期业务操作 |
| --- | --- | --- |
| 待审核 | 程序分流后等待人工初审 | 初审通过、初审不通过退款 |
| 驳回已退款 | 初审不通过且已完成退款 | 查看详情及历史 |
| 打款中 | 审核通过后已进入打款处理 | 查询状态、查看详情 |
| 打款失败 | 明确打款失败，需要复审 | 复审退款、复审通过再次打款 |
| 打款成功 | 打款完成 | 查看详情及历史 |
| 已退款 | 打款失败后经复审已完成退款 | 查看详情及历史 |

流转规则：

```text
发起提现 → 程序分流
  ├─ 自动审核通过 → 自动选渠道 → 打款中
  └─ 待审核
       ├─ 初审通过 → 自动选渠道 → 打款中
       └─ 初审不通过并退款完成 → 驳回已退款

打款中
  ├─ 打款成功 → 完结
  └─ 打款失败 → 复审
       ├─ 退款完成 → 已退款
       └─ 审核通过 → 指定渠道或自动选渠道 → 打款中 → 成功／失败继续循环
```

“审核通过”“修改订单号”“开始第 N 次打款”是历史事件，不是新增订单状态。接口受理成功不等于打款成功；退款只有实际完成才显示相应退款终态。查询超时、提交失败等作为操作／查询错误显示，不伪造为打款失败或退款成功。

## 5. 提现管理主列表

### 5.1 筛选及状态入口

沿用现有筛选：流水号、上游订单号、渠道类型、提现渠道、提现方式、用户 ID、提现状态、国家、发起时间。查询、重置和手动刷新可用。订单号搜索应考虑历史编号关联；实际搜索接口能力由后台落地。

增加六种状态的快捷筛选，另有“全部”。状态数量按当前其他查询条件计算，切换状态不改变其他查询条件。“打款失败”直接作为复审订单入口，不增加“待复审”状态或重复业务页。失败列表提供按提现方式快捷筛选及数量，便于先选方式再当前页全选。

### 5.2 表格

保留现有信息维度：订单／用户、状态、发起时间、提现／到账金额（USD）、实际打款金额及币种／汇率、固定／浮动手续费及费率、渠道类型／渠道／提现方式、钻石扣除前后、收款信息、审核人／时间／备注。

主表全部字段直接展示，不设计字段隐藏、显示字段设置或展开完整字段开关。保留订单／用户、状态与失败原因、提现方式、金额、实际打款、最近渠道、发起时间、手续费、钻石变动、收款信息、审核备注及上游订单号等全部信息。

宽度不足时表格内部横向滚动，固定订单列及右侧操作。支持 20／50／100 条分页，主列表批量选择限当前页；翻页、修改查询或每页条数时清除勾选。关闭浮层保留来源列表筛选、分页及滚动位置。

### 5.3 操作及批量校验

| 操作 | 允许条件 | 提现方式限制 |
| --- | --- | --- |
| 单笔／批量初审 | 全部为待审核 | 可为不同提现方式 |
| 单笔／批量复审 | 全部为打款失败 | 必须为同一种提现方式 |
| 详情 | 所有状态 | 无 |

选中第一笔后，其他处理阶段的订单提前禁选；选择失败订单后，其他提现方式提前禁选，显示限制原因，取消选择后可切换。初审仍允许跨提现方式。不同状态或不同方式混合的列表不直接提供含糊的全部勾选，先筛选或先选一笔，再全选兼容项。

操作按钮根据已选订单提前启用或禁用，进入抽屉和提交时仍重新校验。不静默过滤不符合条件的订单。复审不要求历史使用的渠道相同，只要求提现方式一致。

旧的“失败回退到待审核”“失败回退审核（修改订单号）”由复审入口承接；失败退款收敛到复审结果选择。初审和复审使用独立文案，不合并成含糊的“审核”。

## 6. 初审抽屉

### 6.1 布局

右侧大抽屉，桌面宽度约 1400px，上限受屏幕宽度约束。顶部固定标题、关闭按钮；内容按“本批笔数／金额／提现方式 → 单一结果摘要（提交后） → 本批订单列表 → 本次处理”的顺序排列。抽屉内不再二次筛选或勾选，参数统一作用于从主列表已确定的本批订单。提交初审按钮及本批笔数／金额放在本次处理块内；底部固定区仅保留刷新说明及关闭按钮。

### 6.2 参数

| 字段 | 规则 |
| --- | --- |
| 处理结果 | 审核通过／不通过并退款，必选 |
| 驳回原因 | 不通过时显示，沿用现有初审驳回规则；本次不新增初审原因必填或用户可见规则 |
| 备注 | 选填，管理端内部记录 |
| 渠道 | 初审不提供指定渠道；每笔通过订单根据各自提现方式配置自动选取 |

批量可包含不同提现方式。金额汇总统一使用提现 USD，不将不同实际打款币种直接相加。

### 6.3 提交后

抽屉不自动关闭，本批订单全部保留。通过并受理的订单进入打款中，退款完成的驳回订单显示驳回已退款。单一结果摘要随逐笔状态更新；本次处理参数可收起，展开后仅查看本次记录，不允许原批整批重复提交。

初审打款失败时，按提现方式提供“复审失败订单 N 笔”入口，形成仅包含明确失败订单的下一批复审；可返回原初审批次，原批全部记录和实际状态保留。若初审批次中失败订单有不同提现方式，分别进入复审，不混批。

## 7. 复审抽屉

与初审共用布局规范：本批订单列表在上，本次处理块在下；提交复审按钮放在本次处理块内，底部仅关闭，提交与关闭不并排。单独校验、单独使用复审字段。头部展示本批提现方式；历史渠道可以不同。表格重点展示当前订单号、用户、金额、最近打款渠道、打款次数、失败原因、当前状态和详情入口。

### 7.1 退款

- 处理结果选择“退款”。
- 退款理由必填，明确标注“用户可见”；不能用内部备注替代。
- 可填写选填内部备注。提供可点击且可编辑的常用理由，展示用户可见原文预览，并提示该理由会统一应用于本批订单；不同原因应分批处理。
- 不展示／不提交渠道、修改订单号等继续打款字段。
- 实际退款完成后显示“已退款”，不显示“驳回已退款”。

### 7.2 审核通过、继续打款

| 字段 | 规则 |
| --- | --- |
| 提现渠道 | 默认“自动选择”；其余仅列出该提现方式配置且可用的渠道，不列出全部渠道 |
| 自动选择 | 不明确指定渠道，由程序按提现方式配置的渠道优先级选择并打款 |
| 指定渠道 | 只影响本批订单；不修改全局配置 |
| 修改订单号 | 是／否；新开复审不预选，提交前明确选择；选是由后台分别自动修改每一笔提交订单的订单号 |
| 备注 | 选填，管理端内部记录 |

新开复审不替运营默认沿用旧号，实际提交仍只有是或否，不增加第三种后台参数。保留“部分渠道不允许复用订单号”的就近说明；若渠道实际要求换号，由后台约束并清楚反馈，不能静默改变选择。

提交时重新校验订单仍为打款失败、提现方式一致、指定渠道仍可用。无可用渠道时提示具体原因，继续打款不可提交，但退款入口仍可用。审核通过并受理后显示打款中。后台需要记录“自动／指定”的选择及最终实际使用渠道。

### 7.3 本批失败订单再次处理

抽屉始终保留打开时确定的全部订单，无筛选、复选框、全选、取消勾选等操作。提交后成功、失败、打款中等不同结果直接逐笔展示。

再次打款失败时，提供“复审失败订单 N 笔”入口，进入只包含明确失败订单的固定子批次；新批次重新填写参数并明确提交，不重复处理成功或打款中的订单。可以返回原批完整结果。未受理订单通过“重新处理未受理订单 N 笔”单独进入下一批，与已受理订单分开。

## 8. 两类抽屉共用的布局、提交与刷新规则

1. 主列表选单后确定本批订单；抽屉内不再选单或筛选。顶部仅显示本批笔数、提现合计及提现方式，不平铺六项状态计数卡。
2. 订单列表在前，本次处理在后，参数统一作用于完整本批。按钮明确“提交初审／提交复审”、具体处理动作、笔数及金额，提交与底部关闭不并排。
3. “展开处理参数／收起处理参数”仅放在本次处理标题旁。收起只隐藏参数内容，标题、开关及核单提示始终保留；不把开关放进状态进度区。
4. 标题旁的“先核对上方订单，再填写并提交本次处理”使用红色加粗文字醒目提示。
5. 提交后仅保留一处动态结果摘要，不再同时展示提交轮次消息、六项计数卡和结束进度框。例如“本批已结束 2 / 3 笔 · 打款失败 1 笔”；全部结束时显示“本批已结束 3 / 3 笔 · 全部已结束”。逐笔提交记录与业务状态保留在表格中。
6. 初审、复审提交后均不自动关闭。收起的参数可展开查看，但已提交参数只读，原批没有再次整批提交按钮；失败或未受理通过明确入口形成下一批处理。
7. 每 30 秒刷新一次本批状态，提供手动刷新和最近刷新时间。刷新不移除本批订单、不清空提交前草稿、不跳动滚动位置。
8. 提交前本批某笔状态发生变化时，不静默过滤或缩小批次，阻止原批提交并提示返回主列表重新确定订单。提交时后台仍校验状态、提现方式及可用渠道。
9. 批量逐笔显示提交是否受理与业务实际状态；未受理不显示为打款中或成功。提交期间禁用重复提交及参数修改；结果未知先查询确认，不能直接再次打款。
10. 退款实际完成后才显示已退款或驳回已退款。查询失败保留最近已知状态和成功刷新时间，不伪造终态。
11. 全部结束仍不自动关闭。关闭后停止当前轮询；从最近处理批次可重新查看原批，恢复查看不自动重新执行提交。正式产品需保存批次与订单关联及权限范围。
12. 从抽屉查看详情后关闭详情，返回原抽屉，保留本批、提交前草稿及滚动位置。初审或复审子批次提供返回原批入口。

### 8.1 提交二次确认

初审、复审的所有提交（通过打款、不通过退款、复审退款，以及失败／未受理子批次）都经过二次确认。点击处理块的提交按钮时先校验必填项；校验通过只打开确认弹窗，不更改订单号、不执行退款、不发起打款、不记为已受理。

| 内容 | 展示规则 |
| --- | --- |
| 标题 | 确认提交初审／确认提交复审 |
| 处理结果 | 初审通过并打款、初审不通过并退款、复审通过再次打款、复审退款，按本次选择显示 |
| 订单范围 | 本批 N 笔，全部处理 |
| 提现合计 | 本批提现 USD 合计，不合并不同实际打款币种 |
| 提现方式 | 初审可展示多个方式；复审展示本批同一方式 |
| 打款渠道 | 初审为按每笔方式自动选择；复审显示自动选择或本次指定渠道 |
| 修改订单号 | 仅复审通过时展示是／否，是时明确后台逐笔换号 |
| 退款理由 | 退款时展示原文；复审标注用户可见；初审沿用既有驳回规则 |
| 内部备注 | 已填时单独显示，与用户可见理由区分 |

弹窗操作为“返回修改”和“确认提交”。返回修改或 Escape 只关闭确认弹窗，保留抽屉、固定订单范围和所填参数，不执行任何业务处理。默认焦点在返回修改，避免 Enter 误确认；弹窗打开时底层抽屉不可操作。

点击确认提交才执行。确认时再次校验订单状态、当前订单号／金额／收款资料、参数及渠道可用性；若相较弹窗显示时有变化，阻止提交，提示返回抽屉重新核对，不静默缩小范围或改变参数。提交中禁重复点击和返回；完成后只关闭确认弹窗，抽屉保持打开，继续按原规则展示逐笔结果和单一摘要。

## 9. 订单详情：左右分栏弹窗

### 9.1 容器

沿用详情弹窗，扩大为约 1520px 宽的居中弹窗；左侧约 65%、右侧约 35%，两侧独立纵向滚动，同时可见，不使用页签切换。顶部固定当前订单号、当前状态和关闭按钮，底部保留关闭。详情提供手动刷新，刷新同时更新当前信息及时间轴。

左侧顶部优先展示收款人、收款账户、提现方式和打款金额，失败订单就近展示最近失败原因。现有截图字段全部保留，但其他收款／身份空字段默认折叠，可展开完整查看，不让大量“—”淹没核对信息。分组如下：

| 分组 | 字段 |
| --- | --- |
| 基础信息 | 流水号／当前订单号、上游订单号、用户 ID、国家代码、提现状态、发起时间、打款时间、审核时间 |
| 金额信息 | 提现金额、到账金额、扣除钻石、扣除前／后钻石、固定手续费、手续费费率、手续费金额、打款货币汇率、实际打款金额；清楚标注单位 |
| 渠道与收款信息 | 渠道类型、提现渠道、提现方式、打款货币代码、收款账户、账户类型、账户验证数字、USDT 地址、币安 ID、收款姓名及名／中间名／姓、收款电话、邮箱、银行代码／名称／网点号／城市／代理账号、证明类型、识别号码及有效期、出生日期、地址／城市／州／邮编 |
| 备注信息 | 驳回原因、退款理由（用户可见）、审核人、内部备注；无值显示“—” |

### 9.2 历史时间轴

按事件发生时间从上到下排列，不按最新状态覆盖历史。右侧顶部固定最新进展、实际渠道、累计打款和换号次数，并提供“跳到最新／回到发起”；不必先滚完整条历史才能知道现状。节点保留事件、时间、自动／人工来源、操作人、结果及对应业务字段。长编号换行并可复制，不压缩成不可区分的省略号；刷新保留两侧滚动和展开状态。

| 事件 | 展示内容 |
| --- | --- |
| 发起提现 | 时间、用户、金额及提现方式 |
| 自动审核通过 | 时间、系统来源、通过结果 |
| 人工初审通过／驳回 | 操作人、时间、结果、原因／备注 |
| 第 N 次打款发起 | 次数、实际渠道、本次订单号、时间 |
| 打款失败 | 对应打款次数、渠道、失败原因、时间 |
| 复审通过 | 操作人、时间、自动或指定渠道、修改订单号是／否、内部备注 |
| 修改订单号 | 原订单号 → 新订单号，与本次复审关联；后台确认修改后才记录成功事件 |
| 打款成功 | 对应次数、实际渠道、时间及实际打款金额 |
| 初审／复审退款 | 对应处理阶段、操作人、退款结果、退款理由与时间 |

每轮复审和打款分别留痕，多次失败不能合并成最后一次失败。选择自动渠道也必须展示最终实际渠道。批量操作在每一笔订单的生命周期分别记录，可附同批操作标识用于追溯。换号后仍可查看完整历史及每次实际使用的编号。

示例必须覆盖：发起 → 自动审核通过 → 第一次打款失败 → 复审换号 → 第二次打款失败 → 再次复审换号 → 第三次打款失败 → 再次复审换号 → 第四次打款成功。

## 10. 原型与演示边界

原型为本地 HTML/CSS/JS，使用虚构数据；支持主列表筛选与方式快捷入口、主列表前置勾选限制、20／50／100 条分页、全部字段展示、两类固定批次抽屉、条件字段、退款理由预览、明确换号选择、提交二次确认、模拟执行、30 秒轮询、单一结果摘要、失败／未受理子批次、最近批次回看、导出示例 CSV、左右分栏详情及时间轴定位。25 张场景图由同一交互源文件导出。

模拟打款在受理后等待 8 秒，再于下一次查询反映演示结果；部分示例首次重试失败，再次重试成功，用于验证循环。示例换号由浏览器模拟后台生成；正式环境须由后台完成。最近批次在本次页面打开期间保留最近 10 批，刷新浏览器后清空；正式产品按后台持久化批次查询实现。页面刷新重置全部示例，不保存真实业务数据。提交失败、查询失败、渠道失效和退款失败的生产异常在需求中定义，原型不模拟真实接口、资金账务或并发回调。

现有初审驳回原因的必填和可见性未在本次重新约定，沿用现有规则；原型允许选填。正式接口名称、状态编码、订单号字段映射、自动规则范围和渠道配置数据不在本次设计中指定。
