# SANO直播间互动专项维护规范

## 1. 资料定位

本目录是SANO直播间互动能力后续设计与交流的统一工作区。新增规则、流程、原型和输入资料应按用途归档，避免当前需求、参考资料、导出版和临时验收文件混放。

## 2. 信息优先级

发生内容冲突时，按以下顺序判断：

1. 当前会话中用户最新明确确认的业务规则。
2. `需求文档/`中的当前有效产品需求文档。
3. `设计/原型图/`中的当前流程或页面基线。
4. `资源/需求输入/`中的原始需求确认记录。
5. `资源/历史需求/`中的旧版本资料。

最新规则需要同步反映到Markdown正文、Word交付版及受影响的流程或页面原型中。如果本轮只要求分析交流，不提前修改文件。

## 3. 文档维护

- 当前有效需求统一放在`需求文档/`，不按月份重复建立主文档。
- Markdown是可维护正文；Word是评审交付版本。两者内容必须保持一致。
- 同一需求持续更新原文档；只有用户明确要求保留方案或基线时才新增独立版本。
- 已确认规则写入正文；会影响实现但尚未确定的内容放入“待确认事项”。
- 文档至少覆盖角色职责、模板和快照、累计与触发、提醒与音效、主播履约、观众反馈、状态、异常、风控和数据审计。
- 三步以上流程优先使用图示，同时保留必要文字说明。
- 数据库表结构、接口代码和详细测试用例不写入主产品需求，除非用户明确要求。

## 4. 设计维护

- PNG评审图统一放在`设计/原型图/`。
- 后续如产生SVG可编辑源文件，放在`设计/源文件/`；生成脚本放在`设计/生成工具/`。
- 编号保持稳定；新增页面或流程使用后续编号，修改已有内容优先保留原编号和文件名。
- 管理端页面排在App页面之前，命名使用`编号-端或类型-页面名称`。
- 修改设计后必须检查文字截断、重叠、空白、状态和需求口径，并同步更新`设计/README.md`。

## 5. 资源维护

- 用户提供的脑图、截图、政策文件和原始说明放入`资源/需求输入/`。
- 被当前方案替代但仍需追溯的旧需求放入`资源/历史需求/`，不得与当前有效需求混放。
- 外部平台或法规参考优先在需求文档“参考资料”中保留来源链接，必要时在`资源/README.md`补充用途。
- `.codex_tmp/`、逐页渲染图、视觉验收PDF、调试脚本和其他临时文件不得入库。
- 资源仅作为输入；实际业务规则以用户最新确认和当前有效需求文档为准。

## 6. 核心设计约束

- 配置入口位于直播准备界面；开播后禁止编辑本场模板。
- 平台可配置多个默认模板；每名主播最多保存一个个人模板；每场直播最多启用一个菜单。
- 本场直播使用开播快照，普通配置变更不得影响正在进行的直播。
- 礼物累计维度固定为“同一观众 + 本场直播 + 同一礼物”，下播清零。
- 倍数触发不得丢失任务次数；提醒和公开音效可以合并，但履约必须逐次确认。
- 音效只能选择平台音效库，并在直播间公开播放；主播不得自行上传。
- 主播每完成一次点击“完成1次”，反馈必须准确归属对应观众。
- 暂停、关闭、下播、紧急下架、重复事件和网络重试必须保持任务与进度口径一致。

## 7. 每轮迭代检查

1. 用户最新确认的规则是否写入Markdown和Word需求文档。
2. 平台模板、主播个人模板和本场快照是否边界清晰。
3. 礼物累计、倍数触发、合并提醒和余数计算是否一致。
4. 主播端操作、任务状态和观众反馈是否形成闭环。
5. 暂停、关闭、下播、资源下架和重试逻辑是否相互冲突。
6. 公开音效、内容审核、理性消费和未成年人保护是否覆盖。
7. 图示、正文和需求确认记录是否一致。
8. 新增资料是否进入正确目录，临时验收文件是否被误入库。
