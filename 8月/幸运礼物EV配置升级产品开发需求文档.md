# 第一部分 产品需求

## 1. 功能综合说明

### 1.1 需求背景

当前幸运礼物已经具备新人EV周期和常规EV周期。本次升级不改变两个周期的计算、预生成、进度推进和发奖算法，只升级配置模型。

升级前，幸运礼物直接维护一套新人EV和一套常规EV。升级后：

- 一个幸运礼物可以维护多个EV配置。
- 每个EV配置属于新人或常规中的一种组类型。
- 每个EV配置有且只有一条完整EV明细。
- 本期每个幸运礼物必须有且仅有一个已启用的新人EV配置，以及一个已启用的常规EV配置；两者均作为默认配置。
- 后续接入用户分组后，可为不同用户分组指定不同EV配置；未匹配配置时使用对应类型的默认EV配置。

### 1.2 功能目标

- 将固定的新人、常规参数升级为“礼物—EV配置—EV明细”的可扩展模型。
- 支持一个礼物维护多套新人或常规EV方案，便于复制、调整、审核、发布和切换。
- 保证任一可用礼物始终存在唯一有效的默认新人配置和默认常规配置。
- 保持新人周期只执行一次、常规周期长期循环的现有算法不变。
- 周期初始化时锁定EV配置和版本，避免线上配置变更破坏进行中周期的EV完整性。
- 为后续用户分组匹配EV配置预留数据关系、选择流程和审计字段。

### 1.3 涉及端及职责

| 端/系统 | 主要职责 |
|---|---|
| 管理端 | 维护礼物下的多套EV配置和一对一EV明细；设置类型、默认及启用状态；完成校验、复核、发布、切换和审计 |
| 幸运礼物服务 | 根据用户阶段选择EV配置；初始化周期；推进进度；命中并发放奖励；完成阶段切换和周期重建 |
| 用户分组服务 | 后续返回用户所属分组，供服务端匹配EV配置；本期不参与运行 |
| 金币服务 | 完成礼物消费扣款、奖励金币入账及资金幂等 |
| 配置中心/缓存 | 发布并缓存礼物当前有效的新人、常规默认EV配置及版本 |
| 数据存储 | 保存EV配置、EV明细、用户进度、周期快照和奖励日志 |
| 监控告警 | 监控配置异常、周期进度异常、重复发奖及理论与实际EV偏差 |
| APP | 继续使用现有幸运礼物展示、发送、Combo和结果展示能力，本期无新增交互 |

### 1.4 核心要点

- 幸运礼物与EV配置为1:N，EV配置与EV明细为1:1。
- EV配置类型只能为新人或常规，两个类型不能跨阶段混用。
- 本期一个礼物必须有且仅有一个启用默认新人配置和一个启用默认常规配置。
- 一个EV明细描述一个完整周期，包含周期总价值、周期次数及全部倍率出奖次数。
- 周期总价值等于礼物单价乘以周期次数。
- EV期望值由出奖配置和周期次数计算并严格校验。
- 已开始周期锁定EV配置ID、版本、礼物单价、次数和出奖结果；线上切换不修改进行中周期。
- 新人周期完成后，下一次发送进入常规周期；已完成新人阶段的用户不会再次进入新人周期。
- 常规周期结束后，下一次发送重新选择当时适用的常规配置并生成新周期。
- 默认切换必须原子完成，不得出现无默认或同类型双默认的中间状态。

### 1.5 本期范围

- EV配置和EV明细数据模型升级。
- 管理端配置列表、新建、复制、编辑、查看、复核、发布、启用、停用和默认切换。
- EV计算、配置校验、周期配置选择、版本快照和运行日志。
- 存量礼物配置及用户进行中周期的平滑迁移。
- 并发、幂等、故障恢复和监控告警。

### 1.6 本期不包含

- 用户分组管理、用户分组与EV配置的实际绑定及运行时分组查询。
- 新的EV算法、动态奖池、共享奖池或跨用户周期。
- 幸运礼物APP交互、结算和榜单规则调整。
- 中途重排或强制替换用户已开始的周期。

## 2. 名词定义

| 名词 | 定义 |
|---|---|
| EV | 完整周期总返奖价值÷完整周期总消费价值 |
| EV配置 | 某幸运礼物下的一套完整周期配置组，记录名称、类型、期望EV、周期价值、默认状态等 |
| EV明细 | 与EV配置一一对应的执行参数，记录周期总价值、周期次数和出奖配置 |
| 组类型 | EV配置适用的阶段，只能为新人或常规 |
| 新人EV配置 | 用户首次参与某礼物时执行一次的完整周期配置 |
| 常规EV配置 | 用户完成新人阶段后循环执行的周期配置 |
| 默认EV配置 | 未匹配其他指定配置时使用的兜底配置，按礼物和组类型分别唯一 |
| 周期总价值 | 礼物单价×周期次数，即一个完整周期的总消费价值 |
| 出奖配置 | 一个周期内各中奖倍率及其准确出现次数的完整集合 |
| 未出奖次数 | 周期次数减去所有倍率出现次数之和 |
| 周期快照 | 周期初始化时锁定的配置、版本、价格、次数和出奖结果 |
| 用户分组EV配置 | 后续为指定用户分组绑定的新人或常规EV配置 |

### 3.2 数据关系

~~~mermaid
flowchart LR
    GIFT["幸运礼物"] -->|"1:N"| CONFIG["EV配置"]
    CONFIG -->|"1:1"| DETAIL["EV明细"]
    CONFIG --> TYPE{"组类型"}
    TYPE --> NEWBIE["新人"]
    TYPE --> NORMAL["常规"]
~~~

关系规则：

- 一个礼物可以保存多条配置，用于草稿、历史版本和备选方案。
- 每条配置只属于一个礼物和一种组类型。
- 每条配置必须且只能关联一条EV明细。
- 本期每个礼物的新人、常规类型分别只有一条启用配置，且必须为默认配置。
- 后续用户分组上线后，可允许多条非默认配置被分组绑定，但每个礼物、每种类型仍只有一个默认配置。

### 3.3 用户生命周期

~~~mermaid

    J -- "否" --> F
    J -- "是" --> K["下一次重新选择常规配置并创建新周期"]
~~~

### 3.4 本期配置选择

本期未接入用户分组，只在创建新周期时按礼物和用户阶段选择配置：

~~~mermaid
flowchart TD
    A["确定礼物及阶段"] --> B{"阶段"}
    B -- "新人" --> C["查询唯一启用默认新人配置"]
    B -- "常规" --> D["查询唯一启用默认常规配置"]
    C --> E{"配置与明细是否完整有效"}
    D --> E
    E -- "否" --> F["拒绝执行并告警"]
    E -- "是" --> G["锁定版本和明细快照"]
    G --> H["预生成周期结果"]
~~~

- 已有周期直接使用周期快照，不重复选择配置。
- 缺少对应类型默认配置时，不得用另一类型替代。
- 查询到同类型多条默认配置时，不得随机选择。
- 最终配置无效时，拒绝进入发奖流程并按现有事务规则保证不产生错误扣款。

### 3.5 后续用户分组选择

后续在“创建新周期”节点增加分组匹配，不改变周期算法：

~~~mermaid
flowchart TD
    A["确定礼物及阶段"] --> B["查询用户有效分组"]
    B --> C{"命中对应礼物和类型的绑定"}
    C -- "否" --> D["使用对应类型默认配置"]
    C -- "是" --> E["按后续优先级选出唯一配置"]
    D --> F{"最终配置有效"}
    E --> F
    F -- "否" --> G["拒绝初始化并告警"]
    F -- "是" --> H["锁定配置并生成周期"]
~~~

- 新人阶段只匹配新人配置，常规阶段只匹配常规配置。
- 无分组、服务不可用、未命中或无法唯一决策时，回落对应类型默认配置。
- 用户分组在周期中途变化不影响当前周期，下一次创建周期时重新匹配。
- 已完成新人阶段的用户不会因更换分组重新执行新人周期。

## 4. 管理端功能

建议操作顺序：选择礼物 → 创建EV配置 → 选择组类型 → 维护唯一EV明细 → 校验EV → 保存草稿 → 复核发布 → 原子切换为该类型启用默认配置。

### 4.1 配置列表

列表展示：配置ID、组名称、组类型、EV期望值、周期总价值、周期次数、是否默认、状态、版本、更新时间及操作人。

- 支持按礼物、名称、类型、默认状态、配置状态和版本查询。
- 支持新建、复制、编辑草稿、查看、复核、发布、启用、停用及查看历史。
- 复制配置时同时复制唯一EV明细，新配置为草稿，不继承默认和启用状态。
- 已发布或已被周期引用的配置不可原地修改，调整时创建新版本。
- 已被引用的配置不得物理删除。

### 4.2 EV配置

| 字段 | 必填 | 说明 |
|---|---|---|
| ID | 系统生成 | 配置主键 |
| 礼物ID | 是 | 所属幸运礼物 |
| 组名称 | 是 | 运营可识别的配置名称 |
| EV期望值 | 是 | 目标EV，与明细计算结果校验 |
| 周期总价值 | 是 | 礼物单价×礼物个数 |
| 组类型 | 是 | NEWBIE新人、NORMAL常规 |
| 是否默认 | 是 | 对应类型未命中指定配置时的兜底标记 |
| 状态 | 是 | 草稿、待复核、已发布未启用、已启用、已停用 |
| 版本 | 系统生成 | 每次发布形成不可变版本 |
| 备注 | 否 | 用途或变更原因 |

字段为需求参考，最终命名和公共审计字段以开发设计为准。

配置规则：

- 组名称不能为空，同一礼物下建议唯一。
- 组类型创建后不可直接修改，填错时新建配置。
- EV期望值大于等于0，使用高精度十进制计算。
- 配置周期总价值必须与EV明细周期总价值一致。
- 是否默认不等于是否启用；但本期每种类型唯一启用的配置必须同时为默认配置。
- 草稿、待复核、已发布未启用和已停用配置不得用于新周期。
- 配置必须存在一条通过校验的EV明细后才能发布。

### 4.3 EV明细与计算

| 字段 | 必填 | 说明 |
|---|---|---|
| ID | 系统生成 | 明细主键 |
| EV配置ID | 是 | 关联EV配置，增加唯一约束保证1:1 |
| 周期总价值 | 是 | 与配置周期总价值一致 |
| 周期次数 | 是 | 一个完整周期包含的礼物发送单位数 |
| 出奖配置 | 是 | 全部倍率及准确出现次数 |
| 礼物单价快照 | 建议 | 用于价值校验和历史追溯 |

出奖配置可用结构化JSON或倍率子表实现，最终以开发设计为准；管理端应使用结构化行录入，不让运营直接编辑无校验文本。

示例：周期共2,200次，10倍92次、20倍28次、50倍2次。

| 倍率 | 出现次数 | 返奖倍率贡献 |
|---:|---:|---:|
| 10 | 92 | 920 |
| 20 | 28 | 560 |
| 50 | 2 | 100 |
| **合计** | **122** | **1,580** |

- 有奖次数：122次。
- 未出奖次数：2,200－122＝2,078次。
- 周期总返奖倍率：1,580。
- EV＝1,580÷2,200＝0.7181818，即71.8182%。
- 若礼物单价为P，周期总价值＝P×2,200，周期总返奖价值＝P×1,580。

设礼物单价为P、周期次数为N、第i档倍率为Mi、出现次数为Ci：

    周期总价值 T = P × N
    周期总返奖价值 R = P × Σ(Mi × Ci)
    EV = R ÷ T = Σ(Mi × Ci) ÷ N
    未出奖次数 = N - ΣCi

EV管理端可按百分比展示，数据库应统一保存小数口径，避免71.8与0.718含义混用。

校验规则：

- 周期次数必须为大于0的整数。
- 周期总价值必须等于礼物单价乘以周期次数。
- 如由周期总价值反算次数，则总价值必须能被礼物单价整除；不能整除时禁止保存，不取整。
- 倍率必须大于0，出现次数必须为大于0的整数。
- 同一明细的倍率不得重复；重复倍率合并后保存。
- 所有倍率次数之和不得大于周期次数；差额为未出奖次数。
- 系统计算EV必须与配置期望值一致，默认绝对误差不超过0.0001，超出时禁止发布。
- 计算和比较使用Decimal等高精度方式，不使用二进制浮点结果作为最终依据。
- 配置周期总价值、明细周期总价值、礼物单价×周期次数三者必须一致。

### 4.4 启用与默认规则

本期规则：

- 每个可用礼物有且仅有一个已启用的新人EV配置。
- 每个可用礼物有且仅有一个已启用的常规EV配置。
- 上述两个配置必须分别为新人默认和常规默认。
- 同类型其他配置可为草稿、历史版本或已发布未启用状态，但服务端不得选择。
- 缺少任一类型有效默认配置时，该礼物不能完成EV配置发布或上架校验。

将同类型配置A切换为B时，必须在一次原子操作中：

1. 校验B已发布、明细完整且EV正确。
2. 将B设置为启用默认配置。
3. 同时取消A的启用和默认状态。
4. 刷新配置缓存。
5. 记录A、B配置ID和版本、操作人、复核人、时间及原因。

后续用户分组上线后：

- 每个礼物、每种类型仍只有一个启用默认配置。
- 可存在多个启用的非默认配置，但必须被有效用户分组绑定。
- 非默认配置不得在无绑定时被随机选中。
- 同一用户分组可分别绑定新人和常规配置；缺少其中一种绑定时回落该类型默认配置。

### 4.5 发布、审计与试算

- 建议采用草稿、复核、发布、启用流程，创建人与复核人不得相同。
- 发布前校验礼物状态、单价、组类型、明细唯一性、周期价值、周期次数、出奖配置和EV结果。
- 已发布版本不可原地修改，变更形成新版本。
- 礼物单价变化后，旧配置进入待重新校验；完成复核前不得用于新周期。
- 已开始周期继续使用原价格和配置快照，不回溯修改。
- 紧急停用默认配置前必须选择同类型替代配置，不允许造成默认空缺。
- 操作日志保存修改前后值、操作人、复核人、原因和版本。

管理端建议实时展示：礼物单价、周期次数、总价值、各倍率贡献、有奖及未出奖次数、总返奖价值、期望EV、计算EV和两者差值。

## 5. 服务端运行规则

### 5.1 周期初始化

- 周期仍按“用户ID＋礼物ID”隔离。
- 用户首次发送某礼物时，选择当前唯一启用默认新人配置。
- 初始化时保存配置ID、版本、组类型、礼物单价、周期价值、次数、出奖配置及随机结果。
- 配置快照创建成功后，才能推进本次周期位置。

### 5.2 新人EV周期

- 每个用户针对每个礼物只完整执行一次新人周期。
- 第N次发送完成N次新人周期后标记新人完成。
- 第N＋1次发送选择当前有效常规配置并初始化常规周期。
- 新人默认配置中途切换不影响已开始用户，旧周期继续至完成。
- 服务重启、配置切换及后续分组变化不能使已完成用户重新进入新人周期。

### 5.3 常规EV周期

- 用户完成新人阶段后永久进入常规阶段。
- 常规周期最后一次完成后结束当前周期。
- 下一次发送重新选择当时适用的常规配置并生成新周期。
- 每个常规周期独立随机，不复用固定奖励位置。
- 常规默认配置中途切换只影响后续新周期。

### 5.4 周期生成算法

现有算法保持不变：

1. 读取周期次数N。
2. 按每个倍率和次数生成准确数量的奖励项。
3. 用未出奖结果补齐至N个位置。
4. 对N个结果随机打乱。
5. 保存结果序列，或保存可确定性重放的随机种子、算法版本及快照。
6. 按当前序号逐个读取结果，不在发送时重新计算概率。

结果总数必须等于周期次数，各倍率实际次数必须等于配置次数，完整周期实际EV必须等于配置EV。

### 5.5 批量发送

- 单次发送一个礼物推进一次周期。
- 批量或Combo发送K个礼物时，逻辑上拆为K个连续单位逐个处理。
- 批量跨越新人结束点时，前段使用新人周期，剩余单位进入常规周期。
- 批量跨越常规周期末尾时，完成旧周期后创建新周期并继续处理。
- 每个单位的扣款、周期位置和返奖结果均可追溯。

### 5.6 配置切换影响

| 场景 | 处理规则 |
|---|---|
| 新人配置切换，用户尚未开始 | 首次发送使用新配置 |
| 新人配置切换，用户正在新人周期 | 继续旧快照直至完成 |
| 常规配置切换，用户正在常规周期 | 当前周期继续旧快照，下一周期使用新配置 |
| 用户刚完成新人周期 | 下一次初始化常规周期时使用当时有效配置 |
| 礼物价格调整，用户已有周期 | 当前周期使用价格快照，新周期使用重新校验后的配置 |
| 后续用户分组变化，用户已有周期 | 当前周期不变，下一次创建周期时重新匹配 |

### 5.7 并发、幂等与恢复

- 同一用户、同一礼物的进度推进必须串行或原子执行。
- 同一用户不同礼物相互独立，不使用全用户级大锁。
- 请求携带业务幂等键，相同键只扣款、推进和返奖一次。
- 周期初始化、序号推进、结果读取和完成状态变更应处于同一原子边界。
- 可使用数据库行锁、Redis Lua或等价方案，最终以开发架构为准。
- Redis作为缓存时，持久化存储必须保存可恢复的进度和快照。
- 服务重启或缓存丢失后必须恢复相同周期、序号和结果，不得重新随机。
- 扣款成功后返奖失败时保留原位置和倍率，只重试返奖。
- 奖励日志、金币流水和周期序号使用同一业务流水号关联。

## 7. APP与存量兼容

### 7.1 APP及业务

- APP入口、列表、发送、Combo、特效和结果展示不变。
- APP不展示EV名称、EV值、周期、阶段或用户分组。
- APP不参与配置选择和周期计算。
- 礼物扣款、倍率返奖、主播/公会收益、统计、榜单及活动任务沿用现状。

### 7.2 数据迁移

- 原新人EV迁移为一条NEWBIE配置及其唯一明细。
- 原常规EV迁移为一条NORMAL配置及其唯一明细。
- 两条迁移配置分别标记为该类型启用默认，版本为迁移初始版本。
- 迁移前后校验周期次数、倍率次数、周期价值和EV完全一致。
- 存量进行中周期迁移为周期快照，保留原配置、随机结果和当前进度，不重新生成。
- 已完成新人阶段的用户保留完成标记。
- 任一礼物迁移失败时不得切换该礼物读取新模型。
- 建议先双读校验或按礼物灰度，确认新旧计算结果一致后停止旧模型读取。

## 8. 监控与验收

### 8.1 监控项

- 礼物缺少或存在多条新人、常规默认配置。
- EV配置与EV明细非1:1。
- EV期望值与明细计算值不一致。
- 周期结果总数、倍率次数与配置不一致。
- 同一周期位置重复消费或跳号。
- 完整周期实际EV与理论EV不一致。
- 配置缓存版本不一致。
- 扣款、返奖、进度和日志不一致。
- 存量迁移前后配置或进度不一致。

### 8.2 核心验收标准

- 任一可用礼物只有一个启用默认新人配置和一个启用默认常规配置。
- 任一运行配置有且只有一条有效明细。
- 示例配置计算EV为71.8182%，未出奖2,078次。
- 完整周期各倍率实际次数与配置完全相等。
- 新人第N次仍使用新人配置，第N＋1次使用常规配置。
- 配置切换不影响进行中周期，新周期使用新配置。
- 并发和重试不重复扣款、推进或发奖。
- 服务重启和缓存丢失后进度及剩余结果不变。
- 存量迁移后用户阶段、进度、倍率分布和EV不变。

## 12. 需求口径总结

- 算法不变：新人周期执行一次，常规周期循环，周期内按预生成结果发奖。
- 模型升级：一个礼物有多个EV配置，一个EV配置有且只有一个EV明细。
- 类型隔离：EV配置分新人和常规两类，不能跨阶段使用。
- 本期唯一：每个礼物有且仅有一个启用默认新人配置和一个启用默认常规配置。
- 周期锁定：配置变化不修改进行中周期，只影响后续新周期。
- 后续分组：创建新周期时按用户分组匹配EV配置，未匹配时使用对应类型默认配置。
