## 2. 需求背景

用户基础资料、身份角色、公会关系、资产、充值提现、消费收益、直播和风险数据分散在不同业务模块中。运营人员判断一个用户时，需要在多个页面间反复查询和关联，难以快速形成完整认知。

本需求建设统一的“用户详情（画像）”页面，以用户为中心集中呈现关键信息，并通过摘要、趋势、排行榜和明细记录逐层下钻，帮助使用者快速回答以下问题：

1. 这个用户是谁，当前具有什么身份和关系？
2. 这个用户的资产和商业价值如何？
3. 这个用户今天及最近7天做了什么？
4. 这个用户作为消费者，钱主要花向哪里？
5. 这个用户作为主播，收入主要来自谁、直播表现如何？
6. 这个用户是否存在账号、认证、交易或行为风险？
7. 这个主播在统计周期内为平台带来了多少业务净收入、激励成本和平台贡献净收益？

## 3. 需求目标

1. 在一个用户详情页面内形成完整的用户画像。
2. 首屏优先呈现身份、价值、活跃度和风险等核心判断信息。
3. 汇总数据可继续查看趋势、关系和业务明细。
4. 统一今日、近7天、金额、直播时长、观看人次和主播收入口径。
5. 兼顾信息密度与可读性，避免将全部内容堆叠成一个超长页面。
6. 对实名认证图片、邮箱、IP、资产和交易数据进行权限隔离。

## 4. 全局数据口径

### 4.1 时间口径

- 所有时间均采用服务器时间，时区统一为 **UTC+8**。
- “今日”指服务器时间当日 `00:00:00` 至当前查询时刻。
- “近7天”指今天及前6个自然日，共7个自然日。
- 近7天图表按自然日展示，今日数据展示至当前查询时刻。
- 跨自然日的直播时长按自然日边界拆分后归属对应日期。

### 4.2 金额口径

- 页面汇总金额统一以美元展示，单位为 `$`。
- 金币与美元的固定价值比例为 `10000金币 = 1美元`；钻石与美元的固定价值比例为 `10000000钻石 = 1美元`。
- 各项业务记录在生成时已经完成美元金额换算并保存美元金额，页面直接读取和汇总记录中的美元金额，不再根据金币、钻石、原币或汇率进行二次换算。
- 充值记录和提现记录中的金额均已在记录生成阶段完成换算；页面不承担汇率来源、汇率时点、精度或四舍五入计算。
- 累计充值金额和今日充值金额均只统计支付成功金额。
- 充值订单一旦满足支付成功统计条件，其金额即计入对应今日、近7天或累计充值金额；页面不考虑后续退款、撤销、拒付、冲正和补单对汇总金额的影响。
- 累计提现金额和今日提现金额均只统计最终打款成功金额。
- 今日提现金额按照实际打款时间是否为今日判断，不按照提现申请时间判断。
- 主播普通礼物收入、幸运礼物收入和游戏收入，均指完成分层计算后主播实际获得的分层收入。
- 消费金额、返奖金额和主播分层收入属于不同业务含义，页面不得混合命名或相互替代。
- 测试账号、系统账号、机器人账号和风控无效交易不做额外排除，统一按照业务记录的现有状态参与页面统计。

### 4.3 直播口径

- 单人直播和多人直播根据现有明确的直播类型标识判定。
- PK期间计入哪种直播沿用现有业务逻辑，本需求不额外判断。
- 直播累计观看人次按场次计算：同一用户在同一场直播中无论进出多少次均计1人次；同一用户观看多场直播时按场次分别累计。

### 4.4 身份口径

- 一个用户可以同时拥有高级主播、优质主播、公会长、币商、Payroll、BD、会员等多个角色。
- 各角色相互独立，不得使用单一角色字段互相覆盖。
- 高级主播天数、优质主播天数表示当前连续有效天数。
- 身份取消后停止累计；再次审核通过后从最近一次审核通过时间重新计算。

### 4.5 价值判断边界

- 画像概览分别展示“主播价值”和“用户价值”，不得将两种价值合并成一个总标签覆盖。
- 主播综合评分、用户综合评分及价值标签均使用已有结果或后端配置结果，页面只展示结论与证据，不在前端创建新的评分模型。
- 价值摘要允许展示当前近7天相较前7天的自身变化，用于判断增长或下降趋势。
- **本期不做同类比较**：不展示同国家、同等级、同财富等级、同公会用户的排名、分位或“超过同类多少”的结论。
- 价值结论必须附带可下钻证据；点击收入、消费、活跃、集中度或风险证据时进入对应标签页。
- 风险模块用于说明影响价值判断的风险事实，不在页面前端直接扣减主播综合评分或用户综合评分。

### 4.6 平台贡献净收益口径

- 本指标用于衡量当前主播在所选统计周期内为平台带来的直接经营贡献，指标名称统一为“平台贡献净收益”，不命名为公司整体“平台净利润”。
- 默认统计周期为近7天，即今天及前6个自然日；支持切换今日、近7天、近30天或自定义日期范围，时间统一按 UTC+8 自然日归属。
- 平台业务净收入由以下四部分组成：
  - 普通礼物平台业务净收入 = 当前主播直播间内普通礼物消费总金额 × `16%`。
  - 幸运礼物平台业务净收入 = 当前主播直播间内幸运礼物消费总金额 × `1.1%`。
  - 游戏平台业务净收入 = 当前主播直播间内游戏消费总金额 × `2%`。
  - 道具平台业务净收入 = 当前主播直播间内道具消费总金额。
- 主播激励总成本由直播时长奖励、优质主播奖励、周奖励和其他奖励组成，只统计所选周期内已实际发放成功的金额。
- 平台贡献净收益 = 平台业务净收入 - 主播激励总成本。
- 平台贡献净收益率 = 平台贡献净收益 ÷ 平台业务净收入 × 100%，四舍五入保留2位小数；平台业务净收入为0时显示 `--`。
- 普通礼物、幸运礼物和游戏比例不使用逐笔记录快照。页面按照查询时生效的比例配置计算整个统计周期，并明确展示本次使用的比例；如有配置更新时间则同时展示，跨比例调整周期的数据由授权运营或管理者结合调整时间判断。
- 幸运礼物 `1.1%` 和游戏 `2%` 均已扣除对应的 `0.5%` Jackpot池贡献，因此Jackpot池贡献和实际爆奖金额不得再次从平台业务净收入或平台贡献净收益中扣减。
- Jackpot作为旁路观察信息单独展示：幸运礼物Jackpot池贡献 = 幸运礼物消费总金额 × `0.5%`；游戏Jackpot池贡献 = 游戏消费总金额 × `0.5%`；同时展示统计周期内对应实际爆奖金额，并明确标注“不计入平台贡献净收益”。
- 所有消费、奖励和Jackpot金额直接使用业务记录中已经换算完成的美元金额，页面不进行金币、钻石或汇率二次换算。

## 5. 页面整体布局

### 5.1 页面结构

页面采用“固定用户摘要 + 一级标签页 + 当前标签内容”的结构。

```text
┌─────────────────────────────────────────────────────────────────────┐
│ 返回 / 用户管理 / 用户详情                         刷新  数据更新时间 │
├─────────────────────────────────────────────────────────────────────┤
│ 用户摘要区                                                           │
│ 头像 昵称 ID 国家 性别 账号状态 角色标签 风险标签                      │
│ 财富等级 魅力等级 金币余额 钻石余额 累计充值 累计提现 今日直播时长       │
│ 主播综合评分  用户综合评分  幸运礼物EV                                  │
├─────────────────────────────────────────────────────────────────────┤
│ 画像概览 │ 用户活跃日历 │ 身份与关系 │ 资产与交易 │ 消费与收益 │ 直播分析 │ 风控记录 │
├─────────────────────────────────────────────────────────────────────┤
│                                                                     │
│                         当前标签页内容                               │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘
```

### 5.2 顶部用户摘要区

**核心说明：** 用户摘要区用于完成第一眼判断。使用者不切换标签页，也能识别用户、判断核心价值、确认主要角色和发现明显风险。该区域不是全部基础资料的平铺，而是从全量信息中提取最重要的结果。

展示内容：

- 头像、昵称、用户ID、国家、性别。
- 账号状态、实名认证状态。
- 高级主播、优质主播、公会长、币商、Payroll、BD、会员等已拥有角色标签。
- 财富等级、魅力等级。
- 主播综合评分、用户综合评分、幸运礼物EV；三个指标在同一区域并列展示。
- 金币余额、钻石余额。
- 累计充值金额、累计提现金额。
- 今日直播总时长；单人直播和多人直播的今日时长在“画像概览”中分别展示。
- 当前黑名单、禁止真人认证、封禁、注销等风险状态。
- 页面数据更新时间。

交互要求：

- 用户ID支持一键复制。
- 已拥有角色以标签展示；未拥有角色不在摘要区占位。
- 风险标签优先于普通角色标签，并使用明确文字说明风险类型。
- 点击角色、公会或风险标签，切换至对应一级标签页并定位相关模块。
- 页面滚动后保留精简版摘要和一级标签，方便随时切换模块。

### 5.3 一级标签页

| 标签页 | 核心用途 | 包含模块 |
| --- | --- | --- |
| 画像概览 | 快速完成主播价值、用户价值、活跃和风险判断 | 双价值摘要、今日数据、近7天趋势、关系风险、最近关键事件 |
| 用户活跃日历 | 查看用户长期及当前连续活跃情况 | 累计/连续登录天数、月度同期变化、月度活跃日历、单日活跃详情 |
| 身份与关系 | 查看用户身份、认证、运营及公会关系 | 基础信息、实名认证、主播身份、业务角色、会员、公会、子公会、身份关系事件 |
| 资产与交易 | 查看资金规模、近期变化及资金进出明细 | 资产等级、充值提现汇总、近7天变化、最近成功时间、充值记录、提现记录 |
| 消费与收益 | 分析用户消费结构、收入来源和消费去处 | 今日/近7天消费、返奖、Jackpot中奖、贡献集中度、收入来源Top 10、消费去处Top 10 |
| 直播分析 | 判断主播活跃、经营效率、平台经营贡献和业务记录 | 直播数据、经营效率、平台贡献净收益、趋势、直播间列表、开播奖励记录、PK记录 |
| 风控记录 | 查看当前风险、价值影响、检测证据及历史限制记录 | 价值风险因素、账号异常、认证限制、黑名单历史、挂播记录、直播对比记录 |

## 6. 全局交互规则

### 6.1 数据加载与刷新

- 进入页面时优先加载顶部用户摘要和“画像概览”。
- 其他标签页在首次点击时加载，避免一次性查询全部数据。
- 页面顶部提供手动刷新操作，刷新顶部摘要及当前标签页。
- 页面顶部统一显示本次页面数据更新时间；仅当模块数据更新时间与页面时间不一致时，在模块内部单独标明。
- 单个模块加载失败时只影响当前模块，不阻断其他模块。

### 6.2 通用状态

- 数值实际为0时显示 `0`。
- 无数据时显示 `--` 或对应空状态文案。
- 无权限时显示“无权限”，不得显示成0或无数据。
- 加载中使用骨架状态，不使用旧数据冒充新数据。
- 加载失败时显示失败原因概述和“重新加载”。

### 6.3 通用明细交互

- 所有明细列表支持分页。
- ID、订单号、流水号支持复制。
- 用户ID、公会ID、房间ID存在对应详情页时支持跳转。
- 长文本备注、失败原因、封禁原因默认单行截断，悬浮或点击查看完整内容。
- 时间范围、状态和类型筛选只作用于当前明细模块，不改变页面其他汇总数据。

### 6.4 金额与时长展示

- 美元金额保留2位小数并使用千分位，最终精度按财务规则确认。
- 金币和钻石使用千分位，不转换为美元替代原始余额。
- 时长主要展示为“小时 分钟”，悬浮时展示精确时长。
- 所有图表轴和指标名称必须标明单位，避免金额、金币、钻石或时长混淆。

## 7. 模块详细设计

### 7.1 用户基础信息

**核心说明：** 本模块用于确认用户身份、账号来源、当前状态和最近活跃情况，是客服核验、运营识别和风险调查的基础。基础资料、认证、角色和直播身份应分组展示，避免全部字段混在一张信息表中。

#### 7.1.1 基础资料

展示内容：

- 头像、昵称、用户ID、国家、性别、邮箱。
- 注册时间、注册渠道、注册设备及客户端。
- 最近登录时间、最近活跃时间、最近登录IP及国家、语言。
- 账号状态、账号注销/封禁原因、是否首充。
- 数据更新时间。

展示方式：

- 采用分组信息区展示，不设计成数据库字段表。
- 头像与身份标识集中显示；注册、登录和账号状态分别成组。
- 邮箱和登录IP根据权限脱敏。
- 账号注销或封禁时，状态和原因同时展示，避免只显示状态代码。

交互要求：

- 用户ID和登录IP支持复制，复制能力受权限控制。
- 头像支持点击预览。
- 账号异常原因较长时支持展开查看完整内容。

#### 7.1.2 实名认证

**核心说明：** 实名认证信息用于判断用户身份可信度和认证限制状态。认证结果与禁止真人认证属于不同含义，必须分开显示。

展示内容：

- 实名认证图片组。
- 认证状态。
- 禁止真人认证状态。

展示方式及交互：

- 图片组以缩略图形式排列，点击缩略图预览大图。
- 图片预览增加查看人和查看时间水印。
- 无权限时不返回图片地址，仅显示“无权限”。
- 查看及下载实名认证图片使用独立权限并记录审计日志。

#### 7.1.3 主播及业务角色

**核心说明：** 一个用户可以同时具备多个身份。本模块需要完整表达用户在平台中的多重角色、角色生效时间、等级和运营归属，不允许用单一身份覆盖其他身份。

展示内容：

- 高级主播：是否高级主播、最近审核通过时间、当前连续天数。
- 优质主播：是否优质主播、最近审核通过时间、当前连续天数。
- 公会长：是否公会长、公会成立时间、公会分层比例、实际分层比例、所属运营ID及昵称。
- 币商：是否币商、成为币商时间、币商等级、所属运营ID及昵称。
- Payroll：是否Payroll、成为Payroll时间、所属运营ID及昵称。
- BD：是否BD、成为BD时间、所属运营ID及昵称。
- 会员：未购买、有效或已过期状态，会员等级、生效时间和到期时间。

展示方式及交互：

- 每一种角色作为独立信息块，同一用户拥有多个角色时并列展示。
- 当前有效角色优先展示；未拥有角色可统一放入“未开通角色”区域。
- 高级主播和优质主播天数旁提供口径提示：当前连续有效天数。
- 所属运营ID和昵称组合展示；不同角色对应不同运营归属时分别保留。
- 会员等级、有效期及状态均直接使用现有业务数据，页面不新增枚举，也不重新推导会员状态。

#### 7.1.4 综合评分与幸运礼物EV

**核心说明：** 主播综合评分、用户综合评分和幸运礼物EV用于快速表达用户质量与幸运礼物整体结果，三个指标在顶部用户摘要的同一区域并列展示。幸运礼物EV已有业务结果数据，页面直接查询展示，不执行EV计算或二次推导。

展示内容：

- 主播综合评分。
- 用户综合评分。
- 幸运礼物EV，以百分比展示，示例为 `96.55%`。
- 页面数据更新时间。

交互要求：

### 7.2 用户活跃日历

**核心说明：** 用户活跃日历用于将长期累计活跃、当前连续活跃和每天是否活跃放在同一页面观察，帮助运营快速判断用户是否稳定登录、是否持续开播，以及登录活跃与直播活跃是否同步。该页作为第二个一级标签页，位于“画像概览”之后。

页面布局：

```text
┌─────────────────────────────────────────────────────────────┐
│ 累计登录天数 │ 连续登录天数 │ 累计直播天数 │ 连续直播天数       │
├──────────────────────────────────────┬──────────────────────┤
│              月度活跃日历             │ 选中日期的活跃详情      │
│  月份切换  登录/直播图例               │ 登录时间、登录次数       │
│  周一 周二 周三 周四 周五 周六 周日      │ 直播时长、直播场次       │
│  每日登录、直播及组合状态               │ 当日最近活跃时间         │
├──────────────────────────────────────┴──────────────────────┤
│ 口径提示：UTC+8、累计与连续天数规则、数据更新时间             │
└─────────────────────────────────────────────────────────────┘
```

顶部指标：

- 累计登录天数：历史上发生过有效登录的自然日去重累计。
- 连续登录天数：截至当前仍未中断的连续登录自然日数。
- 累计直播天数：历史上发生过有效直播的自然日去重累计；同一自然日多场直播只计1天。
- 连续直播天数：截至当前仍未中断的连续直播自然日数。
- 累计登录天数指标补充“本月登录天数及较上月同期变化”。
- 累计直播天数指标补充“本月直播天数及较上月同期变化”。
- 连续直播天数补充最近一次连续记录中断日期，帮助识别恢复开播时间。

日历展示：

- 默认展示当前自然月，并支持按月向前、向后切换及快速返回本月。
- 日历以不同颜色和文字标记“已登录”“已直播”；同一天同时发生两种行为时并列显示两个标记，不仅依赖颜色区分。
- 当月未来日期使用禁用状态；非当前月的补位日期降低视觉层级。
- 点击任一日期，在右侧展示当日登录状态、登录次数、首次及最近登录时间、直播状态、直播时长、直播场次和最近活跃时间。
- 无对应行为的日期保留空白，不以0次标记填满日历。
- 四项顶部指标使用页面统一数据更新时间；日历模块显示自身更新时间。切换月份只改变日历内容，不改变历史累计及当前连续指标。

时间及连续口径：

- 自然日边界统一使用服务器时间 UTC+8。
- 跨越零点的直播按照各自然日实际存在的有效直播行为分别标记；同一日仍只计1个直播日。
- 当天已发生相应行为时，连续天数统计至今天；当天尚未发生相应行为且自然日尚未结束时，不立即判定连续中断，仍以前一个完整自然日为判断终点。
- 当前连续记录已经中断时显示 `0天`；累计天数不因连续记录中断而清零。
- 月度变化只比较当前月截至查询日与上月相同日序范围，不做同类用户比较。

### 7.8 直播间数据（近7天）

**核心说明：** 本模块用于综合判断用户作为主播的开播活跃度、房间流水、返奖规模和实际分层收入。直播间消费是房间经营规模，主播分层收入是主播实际所得，两者必须明确分区。

顶部汇总指标：

- 近7天直播时长、直播场次、观看人次。
- 近7天房间消费合计，包含普通礼物、幸运礼物和游戏消费。
- 近7天房间返奖合计，包含幸运礼物返奖和游戏返奖。
- 近7天主播收入合计，为普通礼物、幸运礼物和游戏完成分层后的实际收入。
- 合计指标用于第一眼判断规模；各业务类型的拆分值通过趋势图、悬浮信息或对应明细查看。

直播经营效率：

- 每直播小时主播实际分层收入：近7天主播实际分层收入 ÷ 近7天直播时长。
- 每场平均主播收入：近7天主播实际分层收入 ÷ 近7天直播场次。
- 每场平均观看人次：近7天观看人次 ÷ 近7天直播场次。
- 每百名观看用户产生的房间消费：近7天房间消费 ÷ 近7天观看人次 × 100。
- 近7天付费贡献者数量及其中新增贡献者数量。
- 近7天主播实际分层收入相较前7天的变化比例。
- 分母为0时，对应效率指标显示 `--`；所有效率结果由服务端返回或按统一统计口径生成，页面只负责展示。
- 本期只比较当前主播自身前后周期，不提供同等级主播排名或分位。

#### 7.8.1 平台贡献净收益

**核心说明：** 本模块用于回答“该主播在所选周期内为平台带来多少直接经营净贡献”。它不是主播个人收入，也不是公司整体利润；页面将平台业务净收入、主播激励成本和最终净贡献放在同一条计算链路中，并保留收入、成本及Jackpot观察证据，便于管理者判断主播的经营价值。

模块位置：

- 位于“直播经营效率”之后、“直播趋势图表”之前。
- 画像概览的“主播价值”只抽取近7天平台贡献净收益及相较前7天变化，完整计算和拆分在本模块查看。

统计周期与比例提示：

- 模块右上角提供统计周期选择，默认“近7天”，可切换今日、近7天、近30天或自定义日期范围。
- 模块顶部固定展示本次计算比例：普通礼物 `16%`、幸运礼物 `1.1%`、游戏 `2%`、道具 `100%计入`。
- 比例使用查询时生效配置，不使用逐笔快照；如有比例配置更新时间则一并展示。

顶部指标卡：

- 平台业务净收入：普通礼物、幸运礼物、游戏的平台业务净收入与道具消费之和。
- 主播激励总成本：直播时长奖励、优质主播奖励、周奖励和其他奖励之和。
- 平台贡献净收益：平台业务净收入减主播激励总成本。
- 平台贡献净收益率：平台贡献净收益占平台业务净收入的比例。
- 平台贡献净收益及净收益率为负数时使用明确的负号和风险色，不以0替代。

图表与明细设计：

1. **收入/成本瀑布图：**
   - 按“平台业务净收入 → 主播激励总成本 → 平台贡献净收益”的顺序展示计算过程。
   - 收入为正向柱，成本为负向柱，最终净收益为结果柱；柱体直接标注金额（$）。
   - 悬浮收入或成本柱时展示其业务构成，点击后定位右侧对应明细。
2. **平台业务净收入明细：**
   - 分别展示普通礼物消费金额、采用比例及平台业务净收入。
   - 分别展示幸运礼物消费金额、采用比例及平台业务净收入。
   - 分别展示游戏消费金额、采用比例及平台业务净收入。
   - 展示道具消费金额，并标注“100%计入”。
3. **主播激励成本明细：**
   - 分别展示直播时长奖励、优质主播奖励、周奖励和其他奖励的已发放成功金额。
   - 点击奖励类型时，如已有奖励记录能力，则进入对应记录并带入当前用户和统计周期。
4. **每日贡献趋势：**
   - 使用多系列折线图展示所选周期内每日平台业务净收入、主播激励成本和平台贡献净收益。
   - 横坐标为日期，纵坐标为金额（$）；悬浮同一日期时同时展示三项原始金额。

   - 固定标注“Jackpot仅作观察，不计入平台贡献净收益；1.1%和2%已扣除0.5%池贡献”。
   - Jackpot不进入主指标卡、主瀑布图或每日平台贡献净收益计算，避免重复扣减。

交互要求：

- 悬浮金额时展示原始消费或奖励金额、采用比例、计算后金额及统计周期。

### 7.9 收入来源分析（近7天）

- 幸运礼物。
- 游戏消费。

- 增加日期段筛选，默认今日，按订单创建时间过滤；同时支持按订单号、上游订单号、充值状态和支付渠道筛选。
- 默认按创建时间倒序。
- 订单号、上游订单号、用户ID和币商ID支持复制。
- 点击行或展开操作查看完整订单字段；默认列表保持与原型一致的8列精简布局。
- 国家和币商等级直接读取充值记录中已保存的值，不根据用户当前资料或币商当前等级重新推导。
- 支付金额直接展示充值记录中已换算完成的美元金额，页面不显示或计算换算汇率。
- 金额列右对齐并显示美元单位。
- 失败订单展示失败原因，成功订单展示支付成功时间。
- 点击画像中的累计充值金额时进入全部成功记录；点击今日充值金额时带入今日及支付成功条件。
- 充值汇总只按支付成功状态统计，不因后续退款、撤销、拒付、冲正或补单重新调整。

### 7.18 提现记录

**核心说明：** 本模块用于追溯用户从申请、审核到打款、到账的完整资金流出过程，并解释钻石扣除、打款币种、记录中的汇率、渠道和失败原因。提现金额已经在业务记录生成阶段完成换算，页面不执行金额换算。

列表默认显示：

- 流水号、国家、提现金额与到账金额组合列。
- 扣除钻石。
- 实际打款金额与打款货币代码组合列。
- 提现渠道、提现状态、打款时间。

行展开或提现详情显示：

- 用户ID、扣除前钻石、扣除后钻石。
- 打款货币汇率、渠道类型、提现方式。
- 申请时间、审核时间、到账时间。
- 审核人、失败或驳回原因。

交互要求：

- 增加日期段筛选，默认今日，按提现申请时间过滤；同时支持按流水号、提现状态、渠道类型、提现渠道和提现方式筛选。
- 默认按申请时间倒序。
- 流水号和用户ID支持复制。
- 点击行或展开操作查看完整提现字段；默认列表保持与原型一致的8列精简布局。
- 国家直接读取提现记录中已保存的值，不根据用户注册国家或提现渠道国家重新推导。
- 金额、钻石和汇率分列展示，避免将到账金额与实际打款金额混淆。
- 打款货币代码和打款货币汇率仅作为提现记录信息展示，不参与页面美元金额的重新计算。
- 不同状态下展示对应关键时间：待审核关注申请时间，处理中关注审核时间，成功关注打款和到账时间，失败关注失败原因。
- 点击画像中的累计提现金额时进入全部打款成功记录；点击今日提现金额时带入今日打款时间及打款成功条件。

## 8. 画像概览页组合

**核心说明：** 画像概览不是将全部模块重复展示，而是从各模块抽取最能支持快速判断的数据。详细内容继续进入对应标签页查看。

### 8.1 价值判断摘要

画像概览第一块业务内容为并列的“主播价值”和“用户价值”，两种价值独立展示。

主播价值摘要：

- 主播综合评分及已有价值标签。
- 近7天主播实际分层收入及相较前7天变化。
- 近7天平台贡献净收益及相较前7天变化；点击进入“直播分析”的“平台贡献净收益”模块。
- 每直播小时主播收入、连续直播天数。
- Top 1消费者贡献占比及当前风险结论。
- 点击收入、效率、活跃、集中度或风险证据，分别进入直播分析、用户活跃日历、消费与收益或风控记录。

用户价值摘要：

- 用户综合评分及已有价值标签。
- 累计充值、近7天消费及相较前7天变化。
- 连续登录天数、Top 1消费去处占比及当前风险结论。
- 点击充值、消费、活跃、集中度或风险证据，分别进入资产与交易、消费与收益、用户活跃日历或风控记录。

价值摘要不展示同类排名、分位或同等级比较。

### 8.2 今日关键数据

- 今日充值、今日提现、今日消费、今日返奖、今日Jackpot中奖。
- Jackpot中奖为当前用户今日实际获得的幸运礼物与游戏Jackpot中奖金额合计，与返奖金额分开展示。
- 今日单人直播时长、今日多人直播时长。
- 每项指标点击后进入对应标签页，并自动带入今日条件。

### 8.3 近7天趋势

- 左侧：近7天消费构成，采用按日期排列的堆叠柱状图，分别展示普通礼物、幸运礼物、游戏、商城道具和VIP消费。
- 右侧：直播趋势采用双纵轴组合图；横坐标为日期，左纵坐标为直播小时，右纵坐标为次数并使用“人次/场次”双值刻度。
- 直播时长使用柱状图，观看人次和直播场次分别使用两条折线图。
- 画像概览不重复展示返奖趋势；完整消费趋势、消费构成环形图、返奖趋势和直播经营数据进入对应标签页。

### 8.4 来源、去处、关系与关键事件

- 当前所属公会及运营归属。
- 近7天收入来源Top 3与近7天消费去处Top 3，标题必须明确时间范围。
- 当前有效黑名单和认证限制。
- 展示最近关键事件，包括近期大额充值、连续直播中断、身份变化及风控异常等跨业务事件。
- 默认只展示最近3—5条关键事件，点击进入对应业务标签页查看完整证据。
- 每块提供“查看全部”，进入对应标签页。

## 10. 验收标准

### 10.1 页面结构

1. 页面包含固定用户摘要和7个一级标签页，“用户活跃日历”位于“画像概览”之后的第二个位置。
2. 首屏可直接识别用户、主要角色、核心价值和当前风险。
3. 各模块均包含明确标题、核心说明和数据内容；页面顶部显示统一更新时间，更新时间不同的模块单独标明。
4. 详细数据不会全部堆叠在同一个长页面中。

### 10.2 时间与金额

1. 所有时间按 UTC+8 展示和统计。
2. 今日从当日00:00:00统计至查询时刻。
3. 近7天为今天及前6个自然日。
4. 充值汇总只统计支付成功金额。
5. 提现汇总只统计最终打款成功金额，今日按打款时间归属。
6. 主播收入展示完成分层后的实际收入。
7. 页面直接使用业务记录中已换算完成的美元金额，不进行金币、钻石或汇率二次换算。
8. 充值成功金额不因退款、撤销、拒付、冲正或补单重新调整。
9. 测试账号、系统账号、机器人账号和风控无效交易不做额外排除。
10. 公会分层比例、实际分层比例、记录国家、币商等级和会员状态均使用现有业务记录，不由页面重新计算或推导。

### 10.3 图表与下钻

1. 近7天消费使用多系列折线图展示每日趋势，并使用环形饼图展示近7天消费构成；返奖使用独立趋势图。
2. 直播间消费、返奖和主播分层收入分别展示。
3. 收入来源和消费去处分别支持普通礼物、幸运礼物、游戏Top 10切换。
4. 图表悬浮信息包含日期、业务类型、数值和单位。
5. 图表与明细有下钻关系时，点击后自动带入对应筛选条件。
6. 画像概览的近7天直播趋势以日期为横坐标、小时为左纵坐标、“人次/场次”为右纵坐标，并使用柱状图展示直播时长、两条折线分别展示观看人次和直播场次。
7. 悬浮近7天直播趋势中的任一日期时，同时展示该日直播时长、直播场次和观看人次的原始值。
8. 今日幸运礼物返奖和游戏返奖分别展示，并按各自返奖金额除以对应消费金额计算返奖率，四舍五入保留2位小数；消费金额为0时显示 `--`。
9. 普通礼物收入和幸运礼物收入能够分别按礼物类型查看近7天Top 10。
10. 普通礼物消费、幸运礼物消费和游戏消费能够分别按礼物类型或游戏类型查看近7天Top 10。
11. 直播间普通礼物、幸运礼物和游戏消费能够在同一近7天折线图中按日查看趋势。
12. 主播普通礼物、幸运礼物和游戏实际分层收入能够在同一近7天折线图中按日查看趋势。
13. 直播间列表、PK记录和开播奖励领取记录均支持独立分页，任一列表翻页不影响另外两个列表。
14. 画像概览和“今日消费与返奖”均单独展示今日Jackpot中奖金额，不与幸运礼物返奖或游戏返奖合并。
15. 消费与收益页的七个Top 10图表标题均明确标注“近7天”。
16. 画像概览的收入来源Top 3和消费去处Top 3标题均明确标注“近7天”。
17. 充值记录、提现记录、直播间列表、开播奖励领取记录、PK记录、黑名单历史、直播挂播记录和直播对比记录均提供日期段筛选并默认今日。
18. 直播分析中开播奖励领取记录位于PK记录之前，两者分别保留独立筛选和分页状态。

### 10.4 价值判断与经营效率

1. 画像概览分别展示主播价值和用户价值，不合并成单一总价值结论。
2. 两类价值摘要均展示评分或价值标签以及可下钻的收入、消费、活跃、集中度和风险证据。
3. 近7天变化仅与当前用户或主播自己的前7天比较，本期不展示任何同类排名、分位或同等级比较。
4. 直播分析展示每小时主播收入、每场平均收入、每场平均观看人次、每百人房间消费、付费贡献者数量和收入较前7天变化。
5. 收入来源展示贡献用户数、新增及重复贡献用户数、Top 1、Top 3和Top 10贡献占比。
6. 消费去处展示收益者数量及Top 1、Top 3和Top 10消费去处占比。
7. 画像概览展示最近关键事件，点击事件能够进入对应标签页查看证据。
8. 画像概览的主播价值摘要展示近7天平台贡献净收益及相较前7天变化，并可下钻到直播分析对应模块。
9. 直播分析能够按所选周期展示平台业务净收入、主播激励总成本、平台贡献净收益和平台贡献净收益率。
10. 平台业务净收入按照普通礼物16%、幸运礼物1.1%、游戏2%及道具消费100%计入计算，页面明确展示本次采用比例。
11. 幸运礼物和游戏各0.5%的Jackpot池贡献及实际爆奖金额只在旁路观察区域展示，不重复进入平台贡献净收益计算。
12. 平台贡献模块包含收入/成本瀑布图、收入拆分、奖励成本拆分和每日贡献趋势，切换周期时同步刷新。

### 10.5 用户活跃日历

1. 页面同时展示累计登录天数、连续登录天数、累计直播天数和连续直播天数。
2. 默认展示当前月，并支持月份切换及返回本月。
3. 每个日期能够区分登录、直播、登录且直播以及无活跃四种状态。
4. 点击日期后能够查看当日登录与直播详情，未来日期不可选择。
5. 日历和连续天数统一按 UTC+8 自然日判断；当天未结束且尚未发生行为时，不提前中断连续记录。
6. 页面显示本月登录、直播天数相较上月同期的自身变化，并显示最近一次连续直播中断日期。

### 10.6 多角色与风险

1. 同一用户的多个角色可同时展示，不发生覆盖。
2. 高级主播和优质主播天数按当前连续有效天数计算。
3. 当前生效黑名单和认证限制能在顶部摘要中被识别。
4. 黑名单历史保留类型、期限、状态、原因和操作人。
5. 直播挂播记录能够展示直播间、房主、策略、检测时间、5—10张检测图片及处理状态，并支持独立分页。
6. 直播对比记录能够并列展示直播截图与实名照片，并展示对比分数、一致性结果、策略操作及处罚天数。
7. 直播挂播记录、直播对比记录和黑名单历史的分页及筛选互不影响。

### 10.7 数据状态与权限

1. 0、无数据、无权限、加载中和加载失败状态能够正确区分。
2. 无权限人员无法获取完整邮箱、IP、实名图片或敏感交易数据。
3. 实名图片和敏感财务数据访问留有审计记录。

## 13. 原型逐页开发说明（开发主索引）

**核心说明：** 本章按照7张原型图从上到下的实际顺序编写，是产品、开发和测试核对页面实现的主索引。第4章定义全局口径，第7—8章保留业务背景和交互细节；如模块位置或名称存在理解差异，以本章与对应原型图的一一映射为准。本文只定义页面指标和业务统计，不定义数据库表、字段类型或接口结构。

### 13.1 共用统计规则

| 项目 | 开发口径 |
| --- | --- |
| 当前用户 | 页面顶部用户ID对应的唯一用户；页面内“自己”“当前用户”均指该用户。 |
| 今日 | UTC+8当日 `00:00:00` 至本次查询时刻。 |
| 近7天 | UTC+8今天及前6个自然日；图表按自然日拆分。 |
| 前7天 | 当前近7天开始日前连续7个自然日，不与当前近7天重叠。 |
| 累计 | 该用户满足对应业务条件以来至本次查询时刻的全部有效记录。 |
| 金额 | 直接汇总业务记录中已经保存的美元金额，页面不进行金币、钻石、原币或汇率换算。 |
| 成功充值 | 仅统计业务状态为支付成功的充值记录；日期归属使用支付成功时间。 |
| 成功提现 | 仅统计最终打款成功的提现记录；日期归属使用实际打款时间。 |
| 消费 | 当前用户作为消费者实际扣除的美元金额；不排除测试、系统、机器人或风控无效交易。 |
| 房间消费 | 统计当前主播直播间内全部消费者产生的对应业务消费，不等于当前用户自己的消费。 |
| 主播收入 | 当前主播完成分层计算后实际获得的美元收入，不使用礼物原价或房间消费替代。 |
| 返奖 | 幸运礼物返奖和游戏返奖使用各自业务记录中的实际返奖美元金额。 |

| 付费贡献者 | 近7天在当前主播直播间产生普通礼物、幸运礼物或游戏消费的去重消费者数。 |
| 新增付费贡献者 | 首次在当前主播直播间产生上述有效消费的时间落在近7天内的去重消费者数。 |
| 收入较前7天 | 使用13.1自身周期变化公式比较主播实际分层收入。 |

#### 13.8.3 平台贡献净收益

| 原型指标 | 计算方式 |
| --- | --- |
| 普通礼物业务净收入 | 所选周期房间普通礼物消费×16%。 |
| 幸运礼物业务净收入 | 所选周期房间幸运礼物消费×1.1%。 |
| 游戏业务净收入 | 所选周期房间游戏消费×2%。 |
| 道具业务净收入 | 所选周期房间道具消费×100%。 |
| 平台业务净收入 | 上述四项之和。 |
| 主播激励总成本 | 所选周期实际发放成功的直播时长奖励+优质主播奖励+周奖励+其他奖励。 |
| 平台贡献净收益 | 平台业务净收入-主播激励总成本。 |
| 平台贡献净收益率 | 平台贡献净收益÷平台业务净收入×100%。 |
| 幸运礼物Jackpot池贡献 | 所选周期房间幸运礼物消费×0.5%。 |
| 游戏Jackpot池贡献 | 所选周期房间游戏消费×0.5%。 |
| 实际爆奖 | 所选周期在当前主播房间内实际发生的对应Jackpot爆奖金额。 |

幸运礼物1.1%和游戏2%已经扣除0.5%池贡献。Jackpot池贡献与实际爆奖只进入“Jackpot池观察”，不进入平台业务净收入、主播激励成本或平台贡献净收益。比例使用查询时生效配置计算整个所选周期，不使用逐笔快照。

### 13.10 原型与开发核对规则

1. 开发任务、接口联调和测试用例均以“原型页编号+模块标题+指标名称”标识，例如“原型06/直播经营效率/每百人房间消费”。
2. 原型中出现的每个指标必须能在本章找到统计说明；本章出现的页面指标必须能在对应原型中找到展示位置。
3. 图表汇总值、指标卡和列表使用同一业务口径。点击指标进入明细后，在相同筛选条件下汇总金额应能够对账。
4. 时间字段必须按本章指定字段过滤，不能使用创建时间替代支付成功时间、打款时间或检测时间。
5. 前端只负责格式化和交互，不临时推导评分、身份、分层比例或业务状态；需要计算的金额和比例应由服务端按本章统一口径返回，或由统一统计服务生成。
6. 若后端现有口径与本章不同，开发前必须形成书面差异说明并更新本文，不允许在接口或前端代码中隐含另一套口径。
