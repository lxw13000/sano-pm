# 代理收入主列表查询分析

依据本次提供的sano_proxy、sano_proxy_day_data、sano_anchor_data表结构，以及实际执行SQL中的sano_user.id / proxy_id关联整理。只提供查询方案，不连接或修改业务数据库，不改动页面原型。

完整SQL模板（过程SQL已清理）使用MySQL 8.0 WITH、JSON_TABLE；命名参数由应用驱动绑定，不是直接复制到数据库终端即可执行的变量。未取得实际MySQL执行计划或线上性能数据。

## 当前查询策略：暂不分页

按本次确认，SQL返回全部符合权限与筛选条件的代理，不设置LIMIT/OFFSET，不接收page_size/page_offset，不保留page_rows。SQL保留总条数和每个代理的三项收入，去掉末尾三项全局收入汇总，页面汇总交由前端或服务端累计全部返回数据；结果按proxy_id DESC稳定排序。先观察真实数据量、耗时与执行计划，再决定是否分页及如何优化；尚未连接业务数据库，未取得实际性能数据。

## 字段来源

| 主列表字段 | 来源与处理 |
| --- | --- |
| 代理ID、代理名称、代理长ID | sano_proxy.id、proxy_name、user_id |
| 代理创建时间 | 暂映射create_time，DDL注释是申请时间；如果业务指正式审核通过，需改用audit_time并同步筛选 |
| 所属运营 | 已确认service_user_id实际为BD/直属运营ID，输出operator_id；未提供运营账号表，显示名由既有账号资料补齐 |
| 直属主播数 | sano_user按proxy_id分组统计直属用户，id为用户ID，以id AS user_id关联主播日表；完整用户表DDL及主播纳入条件尚待核对 |
| 开播人数 | 当前直属成员关联sano_anchor_data，统计日期内有记录即计入，按user_id去重；全零和纯语音记录也算开播 |
| 有效开播人数 | 同上，至少一条日记录满足COALESCE(video_minute,0)+COALESCE(many_video_minute,0)>25；按user_id去重，恰好25分钟无效，不跨天累加 |
| 开播率、有效开播率 | 对应人数 / 直属主播数，显示百分数一位小数，分母0返回NULL由前端显示— |
| 收入 | SUM(anchor_diamond_kickback)，直属主播给当前代理的贡献佣金 |
| 子代理收入 | SUM(son_proxy_diamond_kickback)，使用已处理结果，不重复递归加子代理数据 |
| 含子代理收入 | 上述两项之和 |
| 上级代理ID、上级代理长ID | parent_id；父代理记录的user_id。父记录从完整可见范围关联，不受本页业务筛选裁剪，也不越权读取父级资料 |

anchor_income、son_anchor_income的注释是主播业绩，不能替代本次确认的贡献佣金字段。已确认10,000,000 diamond = 1美元。先对原始diamond求和，最后除以10,000,000后按两位小数展示；筛选也按原始金额与美元条件×10,000,000比较，不能先ROUND。输出前将已汇总原始值显式CAST为DECIMAL(50,7)再除，保留diamond对应的美元小数精度，避免整数聚合值直接相除发生中间精度与二次舍入。

## 原始数据先限定范围

| 数据源 | 聚合前的范围限定 |
| --- | --- |
| sano_proxy | 服务端权限ID集合，再叠加代理、代理长、上级关系、运营、创建时间条件；父级资料仍从完整可见集合读取 |
| sano_user | proxy_id仅属于base_proxy，id作为用户ID；只取当前直属成员 |
| sano_anchor_data | live_day位于统计期间，user_id必须匹配direct_members；仅读取用户、两个视频时长及对应代理 |
| sano_proxy_day_data | live_day位于统计期间，proxy_id必须匹配base_proxy；仅读取代理和两项佣金 |

主表anchor_scope使用日表为驱动，FORCE INDEX(day)按时间范围访问，STRAIGHT_JOIN限定用户匹配顺序。之后live_user_stats按代理+用户归并有效标志，再live_stats按代理COUNT/SUM，避免双COUNT DISTINCT。范围外记录不参与业务聚合；CTE可能被优化器合并，书写顺序不等于物理扫描顺序。

本次强制日期优先是针对实测18.838秒、逐用户扫描历史记录的计划调整，仍需重新测量。全平台七天记录很多或只查询很少用户时，该策略未必最优；不要把尚未验证的提速当成既成结果。佣金本次计划为0行，只明确业务范围，不凭空强制其索引路径。

完整可执行范围预筛选验证SQL（过程SQL已清理）固定原计划的20个ID和日期，带EXPLAIN ANALYZE。

## 查询顺序

权限范围 → 基础条件 → 直属成员去重 → 人数、直播、佣金分别聚合 → 每代理一行关联 → 人数/有效人数/收入范围筛选 → 总条数与全部结果排序输出。

不要把主播日数据与代理日收入明细直接同时JOIN后SUM：多位主播、多天记录会产生行倍增。也不要先取一页代理再套人数、有效人数或收入筛选，否则会漏数据、总数和分页错误。程序无需拉取全量主播日明细，只接收数据库按代理聚合后的全部筛选结果。

## 权限集合与前端运营筛选

二者是独立输入，最终同时生效：服务端权限范围 AND 前端业务条件。SQL不重新查询BD上下级；JSON_TABLE只把服务端已查好的ID集合展开成行，方便匹配service_user_id，接口也可以由框架将该集合作为绑定的IN列表。

- permission_operator_ids_json：后端按登录账号计算的完整可见BD/运营ID集合，前端不决定。
- filter_operator_id：页面选择的一个BD/运营ID；未选或选全部时规范化为NULL，不能用它覆盖权限集合。
- can_view_all：后端认证的超级管理员/指定账号标志，只绕过权限范围限制，不跳过前端筛选。

| 服务端权限 | 前端运营筛选 | 最终范围 |
| --- | --- | --- |
| 普通账号：[1001,2001,2002] | 未选择/全部（NULL） | 仅这三个负责人的代理 |
| 普通账号：[1001,2001,2002] | 2001 | 仅2001负责的代理 |
| 普通账号：[1001,2001,2002] | 9999（范围外） | 无结果，可由服务端提前拒绝 |
| 普通账号：[] | 任意值 | 无结果，不能省略权限条件 |
| 超级管理员：can_view_all=1 | NULL | 全部代理 |
| 超级管理员：can_view_all=1 | 2001 | 仅2001负责的代理 |

visible_proxy只做权限限制；base_proxy再按filter_operator_id及其他页面条件筛选。父代理从visible_proxy关联，不能从已按前端条件裁剪的base_proxy关联。例如父代理属于1001、子代理属于2001，选择2001仍应显示权限内父代理的ID与代理长信息。

SQL关键步骤已按1—14标注：权限集合、可见代理、前端筛选、直属成员、人数统计、主播日记录范围、主播期间标志、开播统计、佣金日记录范围、佣金统计、单行关联、指标过滤、总条数、全部结果排序输出。

## 权限及人员范围

已确认service_user_id实际保存BD/直属运营ID。模板直接按后端计算的可见负责人ID集合限制代理；运营A的授权集合须包含A自身及其下属BD账号。没有BD关系表结构，不能仅凭所提供表结构推导这组负责人ID，必须复用已有权限服务。空授权数组返回空列表；超级管理员/指定账号才允许后端设置can_view_all=1。列表运营筛选只在可见范围内进一步缩小结果。

如果子代理记录没有填充其实际负责人，则仅用service_user_id不足以覆盖继承节点，应改接已有最终代理ID权限集合或补全已确认的父子继承规则；本查询不擅自扩大范围。
sano_user使用当前proxy_id归属；主播日记录按这些当前直属用户关联，使用direct_members.proxy_id分组，不以日表proxy_id重新划分归属。代理佣金沿用日表proxy_id。迁移历史数据如果已有处理，两侧应沿用其结果；本SQL不会额外重建归属历史。若表中含非主播账号、注销账号等，是否排除需要依据用户表与已有主播业务标记，不能凭缺失DDL增删人群。

未擅自添加status=1或delete_flag=0。业务如果只允许已通过且未删除的正式代理，应在visible_proxy统一增加条件。根代理parent_id=0输出上级ID为NULL；范围外父代理的代理长资料也返回NULL，不因JOIN泄露。

## 主播日数据统计口径

- 直播统计从sano_anchor_data读取，日期使用live_day；不再查询sano_room，也不再使用create_time/close_time/live_second或room_type条件。
- 期间有任意日记录即算开播，按用户去重；记录时长全零、只含语音时长也计入开播人数。
- 有效开播按单条日记录判断：COALESCE(video_minute,0)+COALESCE(many_video_minute,0)>25。两种视频时长按日相加，空值按0，恰好25分钟无效。
- 期间至少一天达标即算有效主播，同一用户多天达标只算一次。不能先SUM整个期间的时长再判断；例如两天各20分钟不达标。
- 统计日期与代理佣金共用stat_start_day/stat_end_day，两端包含；日期按业务时区生成。日表create_time为统计更新时间，不用于限定业务日期。

## 查询结果与页面汇总

SQL返回全部符合条件代理的15个业务字段和total_count，不执行分页；每个代理保留income_usd、child_income_usd、inclusive_income_usd三个金额字段。

删除末尾sum_income_usd、sum_child_income_usd、sum_inclusive_income_usd以及对应的全局SUM计算。页面三项收入汇总由前端或服务端对返回的全部有效代理行逐项累计，使用精确十进制，累计口径为列表已展示的美元金额合计。

summary CTE仅保留COUNT(*)，每行重复total_count，由应用取首行获取总数。使用summary LEFT JOIN filtered，无符合条件的代理时仍返回一行proxy_id=NULL、total_count=0；应用返回records=[]，三项页面汇总按空列表累计为0，不把这行当作一条代理。

三项页面累计仍对应列表代理各自的收入字段；上下级共同存在时，含子代理收入可能含跨层重复贡献，不能把跨代理相加当作平台去重收益。
