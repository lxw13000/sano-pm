# 公会评估与风险审核：简化表设计

## 1. 定位与边界

本方案用于日常风险扫描、正式周评估、手动重评、版本对比、风险审核列表与详情。采用四张表，不按页面分别建表。

对应[产品需求](公会运营与公会画像.md)第7、8.6、19节。配套[建表SQL](公会评估与风险审核-建表.sql)是新建目标结构，不是现有表的升级脚本，也未在数据库执行。

设计沿用输入SQL的MySQL/InnoDB技术方向，以MySQL 8.0为目标。实际版本、主键类型及项目命名规范须在接入前确认。全部业务时间使用UTC+8，数据库连接时区也须统一；DATETIME本身不保存时区。金额统一美元，计算精度不因展示到美分而降低。

这四张表只保存计算结果、证据和审核，不取代：

- 公会、主播、历史关系、身份、负责人及当前权限数据。
- 日/周经营统计、财务事实、消费收入关联和奖励归属加工结果。
- 充值、提现、钱包流水、订单、文件服务和定时调度系统。

工作台的消费、收益、Top10仍读取经营统计层，不因为没有风险评估结果而无法查询。没有查看真实表结构与数据，本方案不代表指标数据已经齐备。

## 2. 四张表及简化方式

| 表名 | 一行代表什么 | 主要用途 |
| --- | --- | --- |
| `agency_stat_evaluation` | 一次公会、一个范围、一个截止日的一次评估版本 | 任务状态、评分结论、完整结果快照、版本比较 |
| `agency_stat_evaluation_evidence` | 某评估版本中的一条证据 | 风险解释、凭证追溯、跨版本证据比较 |
| `agency_stat_risk_review` | 一次人工审核或复核事项 | 领取、草稿、结论、附件及历史复核链 |
| `agency_stat_review_evidence` | 某审核事项的一条候选或正式引用证据 | 合并多次扫描证据、保存人工最终引用范围 |

将原`agency_stat_evaluation_metric`合入评估表的`result_snapshot`；将原`agency_stat_review_material`合入审核表的`attachments`。不另建任务表、版本差异表、附件表或三种评估各自的结果表。

证据单独建表，是为了分页、引用、去重及保留版本。审核引用关系不能只存证据编号数组：同一事实可能在不同版本中有不同金额或解释，必须同时保存评估ID。

## 3. 评估表设计

### 3.1 字段分工

列表、筛选、排序、统计和关联使用普通列：公会、范围、截止日、类型、版本、任务状态、结果阶段、评分、等级、画像分类、机器结论、负责人、时间、审核事项ID。

指标、评分过程、窗口、数据覆盖及依据版本使用`result_snapshot`。不把整段原始流水塞入快照；大批订单及资金链材料使用独立证据和归档引用。

| 字段组 | 关键字段 | 含义 |
| --- | --- | --- |
| 主体 | `agency_id`、`stat_scope` | 范围1为直属、2为全树；两者独立计算，不累加子公会分数 |
| 历史责任 | `operator_sys_user_id`、`bd_sys_user_id` | 截止日责任人；只用于历史责任归属，不直接授予访问权 |
| 类型 | `evaluation_type` | DAILY日常、FORMAL正式、MANUAL手动 |
| 版本 | `series_id`、`version_no`、`compare_evaluation_id` | 版本序列、序号及明确的对比对象 |
| 幂等 | `auto_task_key`、`request_id` | 自动调度去重、手动重复提交去重 |
| 执行 | `run_status`、`status_reason`、`last_attempt_at` | 等待、运行、成功、失败及原因 |
| 结果 | `result_stage`、双评分、风险等级、画像分类、机器结论 | 阶段与业务结论，不与执行状态混用 |
| 快照 | `result_snapshot`、`rule_version` | 完整结果和解释依据；列表字段与快照必须一致 |
| 审核 | `review_id` | 本次评估触发或合并到的事项；无事项为空 |

### 3.2 执行状态与结果阶段

| 字段 | 值 | 说明 |
| --- | --- | --- |
| `run_status` | WAITING / RUNNING / SUCCEEDED / FAILED | 任务是否完成，与经营好坏无关 |
| `result_stage` | ACCUMULATING / OBSERVING / NORMAL | 数据积累、观察期、正常评估；仅成功任务赋值 |

- 不足7天：任务可以成功，但阶段为ACCUMULATING，综合分数、风险等级及正式画像分类为空；机器结论显示数据积累中。
- 达到7天不足30天：阶段OBSERVING；可以保存按已确认规则可计算的观察指标或分数，不伪装正式经营等级。是否可给分仍遵守产品中的缺失处理与试运行规则。
- 达到30天：可进入NORMAL；仍需单列风险窗口实际覆盖，NORMAL不表示已经拥有完整60天风险数据。
- 等待或失败时，本行评分与结果快照为空，不把前次成功结果复制进来。旧结果单独查询、带原截止日展示。
- 任务完成数＝本批次SUCCEEDED公会ID去重数，包含积累及观察期。正常阶段数另算。工作台已评数也按所选正式批次成功公会去重，并分别标记阶段；待评数为应评公会总数减已评数。范围必须一致，不能把直属与全树各算一家。
- 数据缺失不能填0或解释为低风险；本方案不新增缺失评分算法。

机器结论首期编码为ACCUMULATING（数据积累）、OBSERVING（观察期）、NO_OBVIOUS_RISK（暂无明显风险）、WATCH（建议关注）、MEDIUM_RISK（中风险）、HIGH_RISK（高风险）、SUSPECTED_ARBITRAGE（疑似套利）。观察期的风险线索另在风险字段及快照明确展示，不被OBSERVING字样隐藏。

正式画像分类按产品第18.3节分别使用REAL_OPERATION、OPERATING_WITH_RISK、OPERATING_SUSPECTED、WEAK_SUSPECTED、WEAK_WITH_RISK、LOW_ACTIVITY。积累/观察阶段不套正式分类，portrait_type为空，由result_stage说明原因。是否可计算或发布仍受已确认评分条件约束。

### 3.3 自动、手动及版本

自动任务使用`auto_task_key = 类型:公会ID:范围:截止日`，如`FORMAL:1024:1:2026-10-11`。自动任务的`series_id`等于自身ID、版本V1；同一任务等待/失败重试更新原行，成功后不得重新写入计算结果。

手动请求必须带唯一`request_id`，自动任务的该字段为空；手动任务的`auto_task_key`为空。服务端按类型校验，不能都为空或都填。

- 从已有成功版本、相同公会/范围/截止日发起重评：继承`series_id`，在该序列递增版本，`compare_evaluation_id`为用户选择的原版本。
- 无原成功结果但需要手动评估：创建新序列V1，对比ID为空。
- 选择不同截止日：创建新序列V1，不沿用旧日期的V2。第一版只做同主体、同范围、同截止日的版本对比。
- DAILY的对比ID可指向更早截止日的最近成功DAILY，用于新增风险和证据检测；这是日常变化比较，不是同截止日V1/V2比较。
- 首次FORMAL可引用不晚于本截止日的最近成功同范围评估作触发风险事项的比较基准；没有则为空。不能引用未来数据。
- 多人同时重评时，在事务中锁定序列首行后分配版本号；`(series_id, version_no)`唯一约束兜底。遇唯一键冲突回滚重试，不直接使用无锁MAX+1。
- 手动V2不替代FORMAL V1；默认工作台读取正式主快照，手动结果从版本入口查看。

正式评估周一执行，截止日为上周日。所属自然周由截止日计算，周一开始日不等于执行日期。手动原因覆盖数据修复、关系补录、规则调整、配置调整、人工核验；原因是业务枚举，不单独建配置表。

## 4. 结果快照格式

JSON是固定业务结构，不是任意拼接。必须保存`schema_version`，由服务端校验必填项、枚举、单位和字段一致性。金额与高精度数值使用十进制字符串，应用使用Decimal类计算，禁止先转浮点数再对账。

```json
{
  "schema_version": 1,
  "context": {
    "agency_id": 1024,
    "stat_scope": 1,
    "cutoff_date": "2026-10-11",
    "timezone": "UTC+8",
    "currency": "USD"
  },
  "windows": {
    "week": {"start": "2026-10-05", "end": "2026-10-11"},
    "business_30d": {"start": "2026-09-12", "end": "2026-10-11"},
    "risk_60d": {"start": "2026-08-13", "end": "2026-10-11"}
  },
  "coverage": {
    "business_complete_days": 30,
    "risk_complete_days": 60,
    "missing_sources": [],
    "failed_links": {"count": 0, "archive_reference": null}
  },
  "versions": {
    "data": "data-20261012-01",
    "relationship": "relation-20261011-01",
    "account_classification": "account-20261011-01",
    "ranking_config": "rank-2026-W41",
    "net_income_ratio": "ratio-v1",
    "rule": "risk-v1"
  },
  "metrics": [
    {
      "code": "independent_consume_usd",
      "window": "business_30d",
      "unit": "USD",
      "value": "20000.0000000000",
      "state": "AVAILABLE",
      "reason": null
    }
  ],
  "score_details": [],
  "conclusion": {
    "business_score": null,
    "risk_score": null,
    "risk_level": null,
    "portrait_type": null,
    "machine_conclusion": null,
    "summary": "仅示范快照格式，不代表一条可发布的完整评估结果",
    "business_basis": [],
    "risk_basis": []
  },
  "change_summary": null
}
```

上例仅展示结构。实际成功结果必须保存该阶段所有应有指标、评分依据和结论，不可直接采用示例空数组发布正常画像。

具体要求：

- 窗口必须保存准确起止日及实际覆盖，不能仅用30/60天推断所有指标；周指标、近4周和近8个完整周指标另存对应窗口。
- 指标键为`code + window`，同一快照内唯一；状态为AVAILABLE、MISSING、NOT_APPLICABLE。真实0为AVAILABLE且value为`"0"`，缺失则value为null并说明原因。
- `score_details`保存各分项指标、实际值、阈值、权重、计算方式/参数、贡献分及证据ID。参数版本必须指向不可变配置或归档，不只是一个可能被覆盖的名称。
- `conclusion`保存性质、经营/风险结论、一句话解释、关键依据。主列评分/等级/分类/机器结论须与其一致。
- 非正常阶段允许结果不完整，但必须明确哪些不可计算；不省略原因、不强行套用正常等级。
- 对比页读取两份快照，按指标编码、窗口和单位对齐，计算`新值−旧值`。只对可比数值算差；缺失、单位或窗口不一致标为不可比。不保存另一套差异表。
- 主列中供筛选的评分保留4位小数；原始精度保留在快照。主列由同一次计算按统一舍入规则生成，等级按原始评分判定，不用前端展示值重新判级。

## 5. 证据表设计

证据主键为`evaluation_id + evidence_id`。同一事实跨版本沿用稳定`evidence_id`，本版本摘要、数值和凭证存本版本行，不共享一条可被改写的证据内容。

| 字段 | 作用 |
| --- | --- |
| `rule_code` | 对应命中规则；首期约定一条证据对应一个主要规则 |
| `evidence_grade` | DIRECT直接、STRONG强关联、TEMPORAL时序、BEHAVIOR行为，与产品定义一致 |
| `trace_method` | DIRECT直接追溯、FIFO推定、MIXED混合、NONE不适用；不能与证据等级混用 |
| `requires_verification` | 是否仍有待核验事项，人工材料不自动代表已经核实 |
| `summary` | 可读事实摘要，不直接写成人工已确认套利 |
| `facts_snapshot` | 窗口、实际值、阈值、贡献分、金额、账号、关联关系、来源记录及归档引用 |
| `content_hash` | 业务事实内容摘要，用于识别同编号证据是否有实质更新 |

`facts_snapshot`中的`source_records`可以有多条，每条保存业务类型、原记录ID、发生时间、trace_id及必要金额；资金链保存边的顺序、方向、资产类型和直接/推定性质。另存不可变归档引用及校验摘要，避免钱包原流水清理后只剩一个打不开的订单ID。敏感数据受权限控制，不保存无必要的明文实名材料。

证据ID由规则编码与稳定业务身份生成，不包含评估版本、当前金额、展示排序；无订单的行为证据使用主体、规则及准确统计窗口生成。`content_hash`只计算有意义的事实字段，排除生成时间、排版和展示文案。规范化字段顺序及金额格式后生成SHA-256。

新增证据是ID差集；相同ID但hash变化是证据更新，不能漏报，也不能叫新增事实。日常窗口滚动产生的新行为证据不自动触发审核：仍需满足产品规定的新高等级证据、风险升级等触发条件；重叠窗口和同一事实按规则指纹去重。

成功评估的证据内容不可修改。后续关联修复、人工材料或事实更新进入新评估版本/新证据，不改旧证据。证据与快照及其引用的归档至少保留一年；有未完成事项时不得清理其依据。

## 6. 审核及引用设计

### 6.1 审核事项

| 字段 | 含义 |
| --- | --- |
| `source_evaluation_id` | 首次触发当前事项的评估，创建后不改 |
| `previous_review_id` | 上一次已完成事项；新证据触发复核时填写 |
| `status` | PENDING待审核、IN_PROGRESS审核中、COMPLETED完成、RECHECK待复核 |
| `reviewer_sys_user_id` | 领取并处理事项的审核人 |
| `conclusion`、`reason` | 草稿选择/说明，或提交后的人工结论/依据 |
| `attachments` | 复用现有文件服务的人工核验附件，不存文件二进制 |
| `reviewed_at` | 提交完成时间，草稿为空 |

人工结论枚举：EXCLUDED排除套利、HIGH_RISK确认高风险、CONFIRMED_ARBITRAGE已确认套利；未提交时不是正式人工结论，列表不得据此统计已确认套利。

同公会同范围只允许一个未完成事项，`active_key`生成列及唯一索引保证并发下不重复建单。完成后该键为空，可以为新风险创建复核事项。直属与全树可以各有事项，不混合证据及结论。

首次高风险或其他已确认触发条件：无未完成事项则建PENDING；已有未完成事项则合并。存在已完成结论且满足复核条件时，新建RECHECK并引用旧事项；不把旧事项改回未完成。PENDING/RECHECK领取后进入IN_PROGRESS，提交后COMPLETED。

`evaluation.review_id`表示本次评估归入哪项审核；`review.source_evaluation_id`表示事项首次由哪次评估触发。二者含义不同，不反复同步成“最新评估”。初始触发评估也必须回填review_id；后续合并评估各自填同一个review_id。

未触发新增事项、未合并新事实的评估可以没有review_id。画像如展示已有人工结论，应另查该主体/范围的事项，并明确结论适用版本，不能假装它是本次结论。

### 6.2 候选证据与最终引用

`agency_stat_review_evidence`记录审核证据池，`is_cited=0`为候选，`1`为人工选定引用。合并新扫描时追加对应版本的候选证据，不自动把所有证据当作人工已认可的依据。

提交时校验所有引用同公会、同范围、来源版本已成功且属于本事项的合并评估；同一事实不同版本可以共存，前端按版本展示，不能静默替换。完成后引用集合和附件不可再改。

候选表不是评估归入事项的唯一记录：评估可能因风险升级合并但没有新增证据，该情况仍通过evaluation.review_id保留归属。

### 6.3 附件JSON

```json
[
  {
    "file_id": "existing-file-service-id",
    "name": "业务核验记录.pdf",
    "reference": "file-service-object-reference",
    "uploaded_by": 10001,
    "uploaded_at": "2026-10-12 10:30:00.000",
    "sha256": "由文件服务或上传过程返回的实际摘要"
  }
]
```

只保存长期文件引用，不保存会过期的临时下载链接。下载时重新鉴权。提交前校验文件可用及归属，完成后禁止覆盖文件实体；删除草稿附件不能删除被其他已完成事项引用的文件。

## 7. 写入流程、并发与不可变边界

1. 调度或手动请求创建WAITING评估；命中自动键或请求ID则返回原任务。
2. 工作者以条件更新领取WAITING/FAILED任务，更新RUNNING及尝试时间；已有RUNNING不能再重复领取。
3. 数据未到齐回WAITING并记录具体原因；异常为FAILED。调度器使用现有执行锁/租约及超时恢复能力，不能仅凭last_attempt_at就让两个工作者同时发布。恢复RUNNING前先确认旧执行已失效。
4. 完成计算后，在同一事务中锁定评估行，校验仍持有执行权，写入快照、主列和证据；按触发条件创建/合并审核及候选证据、设置review_id，最后标记SUCCEEDED并提交。任何步骤失败整体回滚。
5. 一旦成功，计算结果、证据、版本及截止日不可覆盖。审核归属仅允许从空绑定一次且有事务校验，不允许重绑；计算内容与工作流元数据分开控制。
6. 审核领取、草稿和提交均锁事项行并校验状态、当前操作者权限。领取用条件更新，避免两人同时领取；不因已有reviewer字段而跳过权限检查。
7. 草稿可更新说明、引用选择及附件。提交检查有效依据和说明后置COMPLETED、设置reviewed_at；完成后禁止修改结论、引用和附件。
8. 新证据/新风险触发复核：新建事项并串联旧事项，不改旧人工结论。

SQL中的主外键保证基础引用存在；同公会、同范围、版本、结果状态及业务枚举等跨字段约束，由服务端统一校验。该校验是方案的一部分，不能只建表而省略。评估到审核的反向引用使用逻辑关联以避免循环建表依赖，服务端事务保证一致，不允许孤立或跨公会挂接。

## 8. 查询与页面对应

| 页面/统计 | 读取方式 |
| --- | --- |
| 日常扫描列表 | evaluation按DAILY、所选截止日过滤；本次未成功时单独查更早成功观察结果，不混入本次完成数 |
| 正式周评估 | FORMAL、固定周日、V1；截止日不随任务延迟而变化 |
| 手动重评记录 | MANUAL及其请求人、原因、状态、序列和对比对象 |
| 画像与历史画像 | 同一评估ID的主列、快照和证据，不读最新日统计拼旧画像 |
| 版本对比 | 同主体/范围/截止日两份快照对齐比较；证据比较ID及content_hash |
| 新增高风险 | 相对compare_evaluation_id从非HIGH到HIGH的公会去重；无历史且首次为HIGH也计新增。HIGH内升级疑似套利单列，不重复称新增高风险 |
| 新增证据 | 以本次与基准版本的证据ID差集计条数；证据更新另列。可进入审核的高等级证据按产品触发规则判断 |
| 审核列表 | review主体、范围、状态、审核人、创建/完成时间；系统结论另带来源评估版本，不用草稿替代 |
| 待审核/审核中/待复核 | 当前状态的事项ID去重数；如卡片写公会数则对agency_id去重并注明是否合并范围 |
| 本周完成审核 | reviewed_at落在当前自然周截至查询时刻、状态COMPLETED的事项ID去重数，不按保存次数 |
| 已确认套利事项数 | 所选审核提交周期内、COMPLETED且结论CONFIRMED_ARBITRAGE的事项ID去重数；不是当前公会数量 |
| 公会最新人工结论 | 对每个公会及范围取最近已完成事项，按reviewed_at、id倒序唯一确定；新待复核事项不覆盖旧结论，但旧结论必须带适用版本且不能冒充新版本结论 |

业务数据仍不含今天；领取、审核、任务进度属于工作流状态，可以实时显示，必须与经营数据截止日区分。正式/日常统计需要明确任务集合、范围和截止日，不能将多个版本或两个范围重复计入完成公会数。

风险数量读取所选批次中可计算的正式结果；积累期/不可计算结果不算低风险。独立保存的MANUAL版本不混进FORMAL V1的总数。

若统计“当前已人工确认套利公会数”，按上述最新已完成人工结论筛选后对公会ID去重，不能累计全部历史确认事项；必须明确直属/全树范围。若询问所选正式批次的人工确认情况，则只使用适用于该批次及证据版本的人工结论，不挪用其他版本。

## 9. 权限、保留与取舍

- 历史运营/BD字段不等于当前授权；所有读取、重评、引用、文件下载和提交，均按当前授权校验。负责人交接不能造成永久越权。
- 全树查看仍需授权；持有父公会权限不自动取得所有子公会敏感证据权限。
- 所有金额、比例、规则和证据由后端产出；JSON不授权前端提交任意评分。
- 附件和已引用证据随审核保留；到期清理由依赖关系校验后执行，不能因基础流水到60天就删除评估依据。
- 四表方案不适合直接对JSON中任意指标做大范围实时排名。如果后续增加这类需求，优先使用已有经营日/周统计层；确实需要评估指标的跨公会自由分析，再增加指标明细表，不预先拆分。
- 不增加自动冻结、追回、提现限制等处置能力。

## 10. 接入与验收

上线前至少验证：

1. 重复自动调度只有一行；失败重试不新增版本；重复手动请求返回原任务。
2. 并发重评获得不同版本；原正式V1不变，版本对比能解释数值和证据变化。
3. 积累/观察期可以执行成功，但与正常阶段、可计算评分明确分开。
4. 同公会同范围并发触发审核最多一个未完成事项；不同范围不串单。
5. 合并扫描追加候选证据且保留评估版本；不会自动勾选为人工依据。
6. 完成结论、引用和附件不可改；复核新建事项，旧结论保持原适用版本。
7. 清理原流水后，已归档证据仍能读取必要事实并解释结论。
8. 工作台不累加多个评估版本，财务排名不依赖评估生成成功。
9. 交接后历史责任显示正确、当前权限正确；附件和证据不能越权下载。
10. 快照与列表主列一致，真实0/缺失不同，单位、窗口与版本可还原。
