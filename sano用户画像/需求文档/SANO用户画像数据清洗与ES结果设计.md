# SANO用户画像数据清洗与ES结果设计

| 项目 | 内容 |
| --- | --- |
| 版本 | V1.2，2026-10-28 |
| 定位 | 《SANO用户标签与价值识别体系》的数据落地配套设计；本文件优先规定数据取得、清洗、保存和可追溯边界 |
| 范围 | 为每个账号并行生成消费者/主播画像、价值、质量、利益依赖、提现与账号关联的历史分析结果；筛选只是辅助入口，本期不自动用于业务处置 |
| 存储决策 | 原始金币、钻石钱包ES记录保留90天；新增清洗结果统一存ES，索引前缀为`sano_user_profile_`，且使用独立于原始记录的保留策略 |

## 1. 先定义结果，再决定清洗什么

目标不是复制现有MySQL表和ES记录，也不是把所有来源强行塞进一张日表。先列出分析问题、所需指标及其统计粒度，再按来源各自的业务口径提取，最后只保存原始记录难以长期提供、重复计算成本高或历史结论必须留存的结果。

| 最终要回答的问题 | 必须具备的结果 | 主要来源 | 清洗后是否单独保存 |
| --- | --- | --- | --- |
| 用户是谁、目前有哪些身份 | 当前身份集合、身份等级及有效期；历史评级使用分析日有效身份 | 用户、认证、会员、公会、币商、Payroll、BD等业务表 | 身份事实仍以业务表为准；在每日评估结果中保存当次身份及关系版本，不复制全量身份流水 |
| 成功充值与消费达到什么程度 | 每日成功充值、本人分类型消费、消费天数和最近行为日 | 充值订单、金币钱包ES | 必要的用户-日可加金额/次数和行为标记保存；明细仍查原来源 |
| 平台内循环与资产流转如何 | 金币来源构成、钻石入账与去向、兑换消费金币/交易金币、成功提现 | 金币/钻石钱包ES、提现订单 | 保存可加的用户-日分类金额；“某笔消费来自哪笔充值或奖励”不在没有来源链时推断 |
| 主播/经营生态贡献如何 | 直播天数/时长、房间消费、分层后收入、主播奖励成本、有效关系范围 | `sano_room`、钱包ES、奖励业务、身份关系 | 保存评级必需的用户-日加总；跨用户去重、关系链按具体问题查询，不能由每日人数相加代替 |
| 价值、质量、利益依赖、关联特征达到什么程度 | C/S/I/E/Q/L/R/D及V等级、组合标签、依据和数据完整性 | 上述指标、历史关系、规则版本 | 每个正式分析日保存一份用户评估结果；规则升级留版本 |
| 提现及关联账号呈现什么特征 | 成功提现、共用收款目标、同安装实例/设备标识/IP的关联及时间跨度 | 提现订单/收款渠道、`sano_log_device` | 成功提现日指标和必要的关系摘要保存；原始敏感字段仍留原业务系统，ES只放受控指纹与摘要 |

设计判据：一个结果若能在90天内直接从原始明细低成本、准确查询，且不需要超90天留存，就不另建“用户-日期-礼物/游戏/收益者”清洗索引。跨90天若需要精确Top、跨日去重或任意期间关联，则必须另存足够粒度的结果；仅有用户每日总额不可能反推这些结果。未建设相应结果时，该能力标为“超出可追溯范围”，不得显示估算为精确值。

## 2. 时间、金额和可追溯边界

1. 权威时区是服务器UTC+8。每个账号均有消费者和主播分析视角，公会、币商、Payroll、BD等业务身份可叠加；“超级主播”与高级主播是同一业务身份。今天的数据可在用户详情中查询展示，但**不进入正式评级、正式标签和趋势比较**。
2. 每日正式任务在T日处理T-1自然日，`analysis_date=T-1`。正式近7天为`T-7 00:00:00`至`T 00:00:00`之前；近30天、90天同理。用户详情既有“近7天=今天及前6天”的展示口径不得混作本体系评级窗口，页面必须标注两者差别。
3. 金币钱包MySQL的`dt`是`create_time`派生的日期，实际消费时刻及小时取`create_time`；充值订单`status=2`，成功时间取`notify_time`，为空回退`create_time`并标记，`day_int`是下单日期不可用于成功日；成功提现仅`status=4`，以`pay_time`归属；设备日志以服务端`create_time`归属；直播按实际覆盖区间跨日/跨小时分摊。不同来源同名字段不自动等价。
4. `10000`业务金币=`10000`业务钻石=`1`美元；数据库钻石数量放大`1000`倍。金币钱包`tokens/10000`、钻石钱包`tokens/10000000`才是用于清洗的美元等值。`amount`是具体商品数量，不是金额。订单已有的美元金额直接采用订单字段，不因页面展示再次换算。
5. 现金充值只计业务成功订单，不重复把钱包充值入账再作为第二笔充值；返奖和Jackpot为金币流入，不是现金充值；主播实际收入为完成分层后的钻石收入，不等于房间消费总额。
6. 金额计算使用十进制精确运算。ES金额字段建议存美元乘`10^10`后的整数，例如`amount_usd_e10`；这能精确容纳数据库单个钻石单位折美元及当前0.16、0.011、0.02、0.005比例的乘积。源字段精度若超过该比例，先完成精度验证和扩容方案，不可静默截断。UI最后再按约定保留2位小数。
7. 原始钱包ES记录保留90天，T+1进入ES。正式90天窗口必须在最老一天原始数据失效前完成提取；失败或晚到时标记覆盖缺口并重跑，不得将缺失视为0。跨90天只展示已保存且粒度足够的清洗结果；不承诺钱包明细下钻，也不承诺旧规则可用不存在的原始明细完全重算。

## 3. 来源逐一解释，不能跨表套用同名字段

### 3.1 金币与钻石钱包ES

参考结构：`sano_wallet_coin_record.json`、`sano_wallet_diamond_record.json`、`sano_wallet_lucky_diamond_record_10m.json`及`EBusinessType.java`。这三个JSON是**mapping**，并非示例业务记录。普通钻石ES承担钻石业务的汇总来源；Lucky钻石ES是幸运礼物短时间段（如1分钟）明细，通常不参与画像汇总。以实际在线索引及业务枚举版本为准。

| 字段 | 解释与校验 |
| --- | --- |
| `user_id` | 本条钱包变动所属用户；金币消费记录中为消费者 |
| `business_type` | `EBusinessType.code`，决定充值、消费、返奖、奖励、兑换或收入的业务含义；不得仅看增减方向分类 |
| `status` | **钱包记录的增减状态**，与提现订单`status`不是同一语义；须与枚举`variation`核对，不是提现成功过滤条件 |
| `tokens` | 本条金币或数据库放大后的钻石变化量；金额计算不得使用`amount`替代 |
| `amount` | 商品/道具等具体数量，不是美元或钱包变动金额 |
| `dt` / `create_time` | 金币MySQL的`dt`由`create_time`生成日期；实际消费小时与日期来源取`create_time`，ES按对应时间值查询 |
| `common_id`、`room_id`、`prop_id`、`ta_user_id` | 金币消费记录`room_id`为房间、`ta_user_id`为接收者、`prop_id`为礼物ID；不能把接收者无条件当房主 |

首版业务映射按枚举核对如下；方向同时由钱包`status`与枚举`variation`交叉校验。枚举新增编码一律先进入“未映射”告警，禁止默默归为其他收入。

| 结果指标 | 钱包类型与`business_type` | 备注 |
| --- | --- | --- |
| 普通礼物消费 / 幸运礼物消费 / 游戏消费 | 金币扣减`1` / `11` / `21` | 本人消费，非房主收入 |
| 道具 / VIP消费 | 金币扣减`41` / `42`、`106` | VIP套餐`106`是否与`42`互斥以实际业务校验；同一记录只入一个分类 |
| 幸运礼物返奖 / Jackpot | 金币增加`16` / `17` | 两者分开，不能计为钻石或现金充值 |
| 游戏返奖 / Jackpot | 金币增加`22` / `26` | 两者分开，不能计为钻石或现金充值 |
| 普通礼物/幸运礼物/游戏主播收入 | 钻石增加`2` / `12` / `23` | 以主播实际分层后入账`tokens`为准；其他代理分账另列 |
| 钻石兑换消费金币 | 钻石扣减`33`、金币增加`34` | 同一兑换的资产两侧，不叠加为新的现金价值；关联键是否可靠需校验 |
| 钻石兑换交易金币 | 钻石扣减`35`、交易金币增加`36` | 币商经营流转，不当作终端用户现金充值 |
| 钱包充值入账 | 金币增加`51`，交易金币`52` | 用于钱包来源及订单对账；成功充值价值C以成功订单到账金额为准，代充渠道分列 |
| 提现扣减 / 退款 | 钻石`53` / `54` | 是钱包事件；成功提现金额以提现订单`status=4`、`pay_time`为准 |
| 主播激励示例 | 钻石增加`74`、`91`、`109` | 周奖励、其他主播成本及全部奖励码需要与产品/财务确认完整映射 |

普通钻石ES直接用于钻石入账、分层收入、奖励和兑换等金额汇总；Lucky钻石ES只在普通钻石记录不能回答且确有幸运礼物明细下钻/类型分析需求时单独使用，绝不与普通钻石汇总相加。幸运礼物收入按礼物类型分析前先核实普通钻石记录是否有可靠`prop_id`粒度，不能从汇总记录凭空反推。

### 3.2 MySQL业务来源

| 来源 | 权威事实与主键 | 用途及不可替代点 |
| --- | --- | --- |
| `sano_wallet_recharge` | `order_no`、`user_id`、`status=2`、`money`、`notify_time`（空时回退`create_time`）、`producer_type`、`ta_user_id` | C为成功充值到账价值，所有成功渠道分列后汇总；`status=3`不是成功，`day_int`不可用于成功日；钱包`51/52`只对账不再相加，实际付款人不明另列 |
| `sano_wallet_withdraw` | `order_no`、`user_id`、`status`、`pay_time`、`money_dollar`、`reality_money`、`user_withdraw_channel_id` | `status=4`才统计成功提现，日期为`pay_time`；申请日/钱包扣减日与打款日分开 |
| `sano_user_withdraw_channel` | 渠道ID及收款账号、USDT地址、币安ID等 | 可生成同收款目标关系；须先确认关联值是申请时快照还是可能被后续修改的当前值 |
| `sano_room` | `id`、房主`user_id`、`room_type`、开关播时间、`live_second` | 主播供给、房间归属。`room_type`已明确单人/多人，不需按PK重判。`online_count`能否代表逐场去重观看人次需单独验真 |
| 上麦、PK记录 | 业务ID、`room_id`、用户及时间 | 分析直播质量和交互；PK分数不能等同消费额 |
| `sano_log_device` | 记录ID、用户、服务端时间、安装实例、设备标识字段、IP及环境字段 | 同安装实例/设备/IP关系和设备市场画像；共享IP、品牌型号仅为弱关联 |
| 身份、会员、登录、公会及代理关系 | 各自业务主键、有效期、状态 | 当前身份可以同时多个；历史E/Q评级必须按分析日有效关系，不能用当前关系倒填过去 |

提现账户标准化应按渠道类型分别处理银行账号、USDT地址、币安ID等。对规范化值生成受控指纹，ES只存指纹类型、用户、首次/最近使用日、次数、成功金额及有效性标记，不存完整账号或证件号。若渠道表非历史快照，只可说明“当前渠道记录所示关联”，不能断言订单发生时共用该收款账户。

## 4. 需要保存的最小ES结果集合

下列是**基于逐人消费者/主播画像及本期分析问题**确定的逻辑结果集合，不意味着把每个原始来源重建一张清洗表。物理上可按日期滚动索引并用读写别名；所有索引名称小写，统一前缀`sano_user_profile_`。配置、原始订单和原始钱包仍保留各自权威系统，不属于这里的清洗结果。

| 索引逻辑名 | 粒度/唯一键 | 保存原因 | 不保存什么 |
| --- | --- | --- | --- |
| `sano_user_profile_metric_daily` | `user_id + stat_date` | 留存评级需要的每日可加金额、次数、行为标记、日末状态和数据覆盖情况；支持任意历史日、7/30/90天趋势及累加 | 不复制订单、钱包事件、礼物明细；不把跨日去重人数存为可直接求和的指标 |
| `sano_user_profile_activity_hourly` | `user_id + stat_date + hour_utc8` | 保存本人消费小时金额/笔数及直播实际覆盖分钟/开播场次，支撑30/90天个人时段习惯和地区策略分析 | 不复制钱包或直播事件；不由登录时刻猜在线分钟；无可信时区时不推断当地小时 |
| `sano_user_profile_withdraw_relation` | `target_type + target_fingerprint + user_id` | 跨账号同收款目标的可查关系摘要，支持超过钱包90天的历史关系展示 | 不存完整收款账号、地址、个人证件及“同一自然人”推断 |
| `sano_user_profile_device_relation` | `relation_type + relation_value_fingerprint + user_id` | 同安装实例/有效设备标识/IP的关系时间跨度、账号切换和关联证据 | 不把IP或相同品牌型号直接当强关系；不复制每条设备日志 |
| `sano_user_profile_assessment_daily` | `user_id + analysis_date + rule_version` | 为每个账号保存消费者/主播及适用经营轨道、主要时段、各等级及V、标签、结构化推断、解释指标、证据和置信度 | 不仅为命中名单者生成；不作为业务动作指令；不保存无法证明的资金来源或违规事实 |

目前**不创建**统一业务事件索引、原始表逐一映射的`clean_*`索引、通用窗口缓存，也不预建用户-日-礼物、用户-日-收益者、用户-日-房间全部维度。未来出现明确的“超90天任意礼物Top/消费去处Top/跨日精确付费人数”等需求时，先补结果所需最小粒度及历史覆盖方案，再新增专用结果索引；不能从已聚合的用户日总额反推。

### 4.1 用户日指标文档

一个用户一天一份**结果文档**，但内部必须按业务语义分组，不能把“本人消费”“其房间消费”“本人分层收入”放在同一金额字段。建议结构如下；字段只在对应来源已接入并通过验收后启用。

| 字段组 | 必要内容 | 聚合/关联规则 |
| --- | --- | --- |
| 主键与覆盖 | `user_id`、`stat_date`、`calc_version`、`source_watermarks`、每来源`COMPLETE/PARTIAL/MISSING` | 固定文档ID按用户+日期；重跑覆盖同一版本结果，不叠加旧结果 |
| 现金与本人消费 | 成功充值金额/笔数；普通/幸运礼物、游戏、道具、VIP消费金额/次数；当天是否充值/消费 | 充值取订单；消费取金币钱包分类；成功充值金额不能由钱包充值入账二次累加 |
| 本人金币流入 | 幸运返奖、幸运Jackpot、游戏返奖、游戏Jackpot、充值金币、钻石兑换消费金币、其他奖励金币、交易金币来源 | 每类单列；交易金币与可消费金币分开 |
| 本人钻石流入/支出 | 普通/幸运礼物和游戏分层收入、主播奖励、其他奖励、兑换消费金币扣减、兑换交易金币扣减、其他支出 | 以钻石钱包业务类型和实际`tokens`分组；成功提现另取订单 |
| 提现及资产状态 | 成功提现金额/笔数、日末金币/钻石余额、余额是否可用 | 成功提现以打款日期统计；日末余额是状态量，不可按窗口求和 |
| 主播供给及房间贡献 | 单人/多人实际直播时长、场次、>=600秒有效直播日标记；房间全部/外部普通礼物、幸运礼物、游戏消费；已确认激励成本 | 房间归属按`room_id -> sano_room.user_id`；E_HOST外部消费排除房主本人，平台经营净收入仍用全部房间消费；实际分层收入另列 |
| 登录/活跃及关系 | 登录/活跃标记；分析日有效经营身份/关系版本引用 | 登录数据来自自身业务日志；公会、BD等关系需时点有效性 |

金额字段用明确的单位后缀如`*_usd_e10`。次数和天数用整数，`*_day_flag`用布尔。不存在业务事实可记0；必要来源不可用则标记缺失且对应指标为`null`，不能写0。对已清洗指标保存来源计数、来源时间水位和口径版本，供复算与解释。

`sano_user_profile_activity_hourly`按`user_id + stat_date + hour_utc8`保存本人消费金额/笔数/类别和每小时有效直播秒数/开播场次。金币消费按create_time归小时；同一房主有效直播区间求并集再与小时取交集，跨日拆分；live_second与时间区间无法核对时标部分覆盖，不猜暂停位置。习惯按主文档第8.2.1节枚举连续3小时段、计算各行为日归一化占比的平均值，>=5日且均值>=40%、覆盖>=50%、单日集中<=50%才称稳定。没有可信时区不推断当地小时，半小时/45分钟时区必须从精确事件重分桶。

### 4.2 关系结果文档

提现关系与设备关系分别生成，避免将“同收款目标”与“同IP”混成相同置信度。每条关系结果至少含关系类型、受控指纹、用户ID、首次与最近出现时间、来源记录数、关联账号数或引用、来源有效性、重算时间。设备关系的`app_install_id`可作为一次安装的中等证据，但不是永久物理设备；MAC字段口径沿用现有`adId/deviceId`，不能因为列名为`mac`就称为硬件MAC。IP可能共享或变化，只作弱证据。

### 4.3 评估结果文档

建议保存`analysis_date`、`user_id`、`current_identities`、`as_of_identities`、消费者与主播两条视角、适用经营轨道、各自主要时段、`primary_value_track`、C/S/I/E各轨道/Q各轨道/L/R/D、V、组合标签、逐人结构化推断和关注主题，以及每个结果的`rule_version`、`threshold_version`、`window_start/end`、实际输入指标、证据编码、来源覆盖、不可评估原因。未消费/未开播与数据缺失分别表示，所有账号都生成该文档，不仅命中名单者。等级和标签可放一份用户-分析日结果文档，不必为每个等级再建一张结果表；筛选和群体视图由逐人结果派生。


比例、净收益等派生值可存评估时采用的配置版本和计算值，但不要求将平台利润率写回每笔历史消费。主播经营贡献按确认口径计算：

```text
房间平台收入 = 房间普通礼物消费×0.16 + 房间幸运礼物消费×0.011
             + 房间游戏消费×0.02 + 归属该房间的道具消费
主播激励成本 = 直播时长奖励 + 优质主播奖励 + 周奖励 + 其他已确认主播奖励
平台贡献净收益 = 房间平台收入 - 主播激励成本
```

幸运礼物、游戏净利润率已扣除各自0.005 Jackpot池贡献，不能再扣一次。道具消费只有业务上能明确归属该主播/房间时才进入对应贡献；否则标记未归属。奖励/成本映射未完整时净收益为部分成本口径，不输出确定盈利；本版Q只衡量行为持续性，不因奖励成本缺项被整体阻断。个人与房间两种净收益、奖励回收比按主文档第9.4节分别计算，不能相加为平台总额。

## 5. 从原始数据到结果的执行流程

### 第一步：把指标合同写清楚

对每个指标登记：指标编码、用途等级/页面、主体（本人/房主/公会等）、日期字段、来源、业务状态、业务类型集合、单位、聚合函数、去重方式、是否可跨日相加、缺失条件、来源关系有效期及负责人。例如“成功提现金额”=提现订单`status=4`且`pay_time`属于统计日的`money_dollar`总和；它不等于当日钱包`53`钻石扣减，不等于申请日金额。

### 第二步：按来源分别提取和校验

1. `sano_wallet_recharge`只取`status=2`、金额`money`、时间`notify_time`为空回退`create_time`，按到账用户/日和producer_type分列；所有渠道成功订单形成C的到账价值，`day_int`不用于成功日，实际付款人未证实不阻断到账C。
2. 金币钱包按`business_type`、钱包`status`、`tokens`解释本人消费、返奖、Jackpot、兑换入账、直接金币奖励；消费实际时间取`create_time`，`dt`是其生成日期；`ta_user_id`为接收者、`room_id`为房间，保留`prop_id`用于90天内所需Top，不预先拆成通用事件表。
3. 普通钻石ES独立解释分层后收入、奖励、兑换扣减，是汇总金额来源；Lucky钻石ES仅在明确的幸运礼物分钟明细问题中单独使用，不参与总体金额相加。金额单位按数据库放大1000倍处理。
4. 提现订单独立解释申请、状态及成功打款；成功金额按`pay_time`统计。收款渠道依其历史快照有效性生成关系。
5. 直播、登录、身份、邀请、设备及互动各按自身业务时间与状态解释；历史身份关系按有效期关联，直播间消费通过`room_id`和房主关系归属；邀请上麦/自行上麦、在线分钟、公频/私聊无来源或计算规则时标记不可评估。
6. 同一来源内按业务主键处理重复采集/重跑；钱包业务自身已防重复，不凭金额、时间相同来合并合法记录。

### 第三步：生成用户日结果和关系摘要

按来源先产出已经解释过的“用户-日-指标”批量中间结果，随后按`user_id + stat_date`汇入用户日文档；消费与直播另按用户-日-小时生成时段结果。这些中间结果可在任务内存或临时作业空间中完成，**不是需要长期保存的每来源清洗表**。关系类按收款目标或安装实例/设备/IP分别汇总至两个关系索引，不挤入金额日文档。

### 第四步：生成窗口、等级、标签和解释

从已完成日指标和小时结果计算正式7/30/90天及上一等长窗口。可加金额、次数求和；日标记求和得到天数；余额取窗口首尾状态；连续天数按日标记逐天计算；比例由窗口分子和分母重新计算，不能平均每日比例。跨日唯一人数和Top不能相加每日唯一数：90天原始可用范围内查相应明细并跨日去重；超过范围只有另存足够粒度时才能给出精确结论。

随后按主文档V1.4的公式生成C/S/I/E_HOST/Q/L/R/D和双V、标签与中文推断。先生成全体窗口指标，再批量生成同窗分布，最后计算每个账号分数；不能逐账号边计算边改变样本人群。其他经营身份E尚未适配则明确未接入，不套用主播公式。必需来源缺失给X/不可评估，新账号不足28日给Q/V观察中，已知无行为与二者区分。

### 第五步：校验、发布和重算

先把T-1数据标记为`BUILDING`，校验源记录计数与分类金额、订单与钱包对账、资产方向、未映射业务码、源时间水位、来源覆盖率、来源重叠及抽样用户明细后才发布`COMPLETE`。失败可重跑同一日期、同一规则版本，文档ID稳定并整体覆盖，不做增量相加。迟到数据或规则变更产生新`calc_version`/`rule_version`并重算受影响日期及其后的窗口评估，旧版历史评估按保留策略保存以供对照。

## 6. 结果如何计算：以主文档V1.4为执行规则

字母是内部代码，接口和页面显示中文名称。等级、时段和推断的公式统一以《SANO用户标签与价值识别体系》V1.4第10—14节为准，不在两份文档维护不同权重。

| 结果 | 必需清洗输入 | 明确用途与计算边界 |
| --- | --- | --- |
| 成功充值价值C | 成功订单30日金额、日数、最近日、渠道；全体同窗正样本分布 | C=金额百分位70%+充值日数分20%+最近分10%；所有成功渠道按到账账号计，不声称证明本人付款 |
| 金币消费价值S | 五类消费30日金额、日数、最近日、分布 | 同类70/20/10权重，日数满分参考10日；社交互动不再占未定义分数 |
| 钻石回投程度I | 33兑换消费金币X、35兑换交易金币Y、成功提现扣除钻石等值Z | X/(X+Y+Z)；Z用订单diamond/10000000并按pay_time；53不与Z再相加；高回投不是质量结论，不进入V |
| 主播经营价值E_HOST | 外部房间消费、窗口精确去重付费人数、有效直播日、付费日 | 40/30/20/10四项明确公式；不认领送礼者全部充值；其他经营身份E待各自适配 |
| 持续行为质量Q | 主行为日数、四个7日段、相邻两个14日主行为量 | 40/30/30；消费者以消费、主播以有效直播为主行为；平台净收益另列 |
| 奖励依赖L | 完整确认的奖励编码及全部金币/钻石正向流入 | 两种资产奖励流入占比取max×100；返奖/Jackpot另列，不单凭高L认定薅利 |
| 关联组合R | 历史有效收款目标、稳定安装实例/设备、IP和已启用行为事件 | 按关系域及奖励时序、互送、同类领奖、低奖励回收分级；72小时区间按并集且需回看窗口前72小时，订单和奖励记录各只计一次 |
| 数据完整度D | 必需指标-日覆盖及缺失原因 | 完整率不是推断概率；关键输入缺失即该维度X，不能用整体95%覆盖豁免 |
| 双视角综合V | C/S/Q_USER，E_HOST/Q_HOST | V_USER=40/40/20且最终等级不超过max(C,S)；V_HOST=70/30且不超过E_HOST；I/L/R独立展示 |

奖励与房间成本映射缺失会影响L和完整净收益，但不应因为缺少私聊/公频/在线会话而阻断已定义C/S/E_HOST/Q的计算。初始权重、日数、金额与时段门槛由主文档明确为设计默认值，运营以后按样本校准，不让开发者临场解释。

主文档第21节包含日指标来源字典、充值提取SQL语义、从原始金额到双V与中文推断的算例，以及边界测试向量。新规则发布须逐个通过相同向量。

## 7. ES生命周期、历史覆盖和查询边界

1. 原始金币、钻石钱包ES索引保留90天；新增`sano_user_profile_*`结果索引使用独立生命周期，不能继承原始90天删除策略。结果保留期限按历史对比、回测、审计及容量另行配置，至少须覆盖产品要求的最长分析历史；变更前做容量测算。
2. 每个结果保存`source_window_start/end`、各来源最大`dt/pay_time/create_time`水位、生成时间、计算版本、规则版本和覆盖状态。结果的存在只证明已计算；有缺口时不宣称全量历史。
3. 超过90天的累计金额、逐日趋势、等级历史可从保存完整的日结果和评估结果展示。钱包单笔明细及未保存对应粒度的历史Top/独立人数不可追溯。
4. 新规则若只依赖已保存的日指标，可按新版重评；若需要已过期的`prop_id`、`ta_user_id`、单笔时间序列等明细，历史只能沿用旧版、展示“无法按新版重算”或启用此前就已留存的专项结果，不能编造历史。
5. 索引写入使用稳定文档ID、明确mapping和别名；按分析日期滚动/分片，避免为每个用户建索引。原始库仍是业务权威；ES结果具备可重建范围说明、备份与权限控制。敏感指纹使用专用密钥和最小授权。

## 8. 首期实施与验收

1. **先补指标合同与来源映射**：充值`status=2`、`notify_time`回退和`money`已确认；金币`create_time/ta_user_id/room_id`已确认；普通钻石ES为汇总、Lucky分钟明细通常不用已确认。金币方向按已给结构和枚举的1增加/-1扣减校验；待接入的仍有提现渠道历史快照、完整奖励/成本编码与事件精度、房间道具归属、在线会话/邀请/互动字段和历史经营身份适配。未确认项标为`PENDING`，不纳入精确结论。
2. **接入并回填**：以现有可取得的MySQL永久记录及钱包ES90天记录回填；90天之外的钱包相关日指标若此前未留存，记录历史覆盖起点，不填0、不假装完整。
3. **发布用户日与小时结果**：至少覆盖充值、五类消费、幸运/游戏返奖和Jackpot、三类主播收入、兑换、成功提现、直播供给、房间贡献、奖励成本、消费/开播小时和来源覆盖标记；在线时长等未确认来源暂不伪造。关系索引与金额日指标分别验收。
4. **发布逐人评估结果**：全部子项、阈值、硬条件和降级规则先完成边界样例测试，再按T-1为每个账号计算消费者/主播及适用经营轨道的等级、标签、推断和证据；无行为与未评估分开，列表仅由逐人结果查询得到。
5. **抽样对账**：逐条核对充值订单与现金指标、钱包业务码与本人消费/返奖/收入、提现成功订单与打款日、房间消费与主播分层收入、设备日志与关系摘要；同一业务事实不在同一指标重复计算。
6. **历史与缺失测试**：测试跨日、月末、90天边界、迟到数据、源索引过期、零分母、身份切换、收款渠道变更、同IP多账号、规则升级和重跑；结果须明确`完整/部分/不可评估`。

本设计确立“逐人画像结果→指标→来源→清洗→保存→评级→解释”的闭环。它不替代独立等级的数值阈值和评分规则验收；《SANO用户标签与价值识别体系》V1.4已给出中文代码对照、逐项闭合公式、初始默认门槛、时段/群体/推断规则与完整算例。尚未提供结构或计算规则的来源必须标记不可评估，不凭猜测补齐。
