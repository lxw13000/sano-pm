## 1. 背景与目标
### 1.1 项目背景
为提升平台直播内容质量，激励主播保持高频、高质量的直播产出，平台计划推出“优质主播”激励体系。该体系旨在通过明确的任务指标与奖励机制，筛选并扶持一批高活跃度、高互动性的主播，同时通过H5端便捷申请与管理端高效审核，形成闭环运营。

### 1.2 核心目标
+ **H5端**：提供便捷的优质主播申请入口、任务进度可视化（含服务端统一倒计时）、奖励领取功能。
+ **管理端**：实现主播配置、申请审核、周数据核算、奖励发放的全流程数字化管理。
+ **数据准确性**：通过服务端统一时间戳与倒计时，彻底解决多时区用户因本地时间差异导致的统计不一致及潜在作弊风险。

## 2. 功能设计
### 2.1 管理端功能设计
#### 2.1.1 主播配置
+ **功能描述**：针对不同国家/地区设置差异化的优质主播考核标准。
+ **配置项**：
    - **开放国家**：下拉选择或手动输入国家代码。
    - **高峰时间段**：设置每日高峰起始时间点、结束时间点。
    - **高峰时长要求**：高峰时间段内每日至少需直播的小时数（默认2小时）。
    - **每日总时长要求**：自然日内至少需直播的小时数（默认3小时）。
    - **每周有效天数**：每周需达成上述时长要求的最少天数（默认6天）。
+ **数据约束**：每个国家仅允许存在一条有效配置记录。

#### 2.1.2 优质主播审核
+ **功能描述**：处理H5端提交的优质主播申请，管理主播签约状态。
+ **列表字段**：主播ID、申请时间、审核状态、审核人、审核理由、审核时间、**<font style="color:rgb(216,57,49);">签约类型（周、月）、签约奖励（钻石）</font>**。
+ **状态流转**：
    - **待审核**：H5提交后的初始状态。
    - **审核通过**：运营确认符合优质主播标准，生效签约。
    - **失效**：审核通过后，运营可手动置为失效。**<font style="color:rgb(216,57,49);">失效14日</font>**后主播可重新发起申请，重新申请后状态重置为“待审核”。
    - **禁止**：运营手动禁止，该主播无法再发起任何申请。

#### 2.1.3 主播周数据
+ **功能描述**：按周维度统计优质主播的核心直播数据，支持运营审核以确认奖励发放资格。
+ **统计周期**：每周一凌晨自动统计上一周（自然周）数据。
+ **列表字段**：
    - 直播间观看用户累计总数（每场去重），ABC 观看两场直播，累计数值为6
    - 直播间观看用户总数（全周去重），ABC 观看两场直播，累计数值为3
    - 直播间停留15s人数（每场去重），ABC 观看两场直播,,每次都超过15秒，累计数值为6
    - 直播间停留时长中位数（预留字段，字段保留，业务还未想好）
    - 直播间消费人数（去重）
    - 直播间消费总数（累计流水）
    - 直播间幸运礼物消费数（累计流水）
    - 直播间游戏消费数（累计流水）
    - 邀请数据（周内邀请总人数）
+ **审核机制**：
    - 运营审核为“合格”后，系统自动生成当期奖励数据，并记录审核人、审核时间、审核原因。
    - 支持按主播ID筛选，默认展示当前周数据。
    - 支持查看每日明细数据（按天汇总）。

#### 2.1.4 主播奖励记录
+ **功能描述**：记录所有优质主播的奖励发放明细。
+ **列表字段**：主播ID、奖励金额、领取状态（待领取、已领取）、领取时间。
+ **排序规则**：按时间倒序排列。

### 2.2 H5端功能设计
#### 2.2.1 Banner宣传页
+ **功能描述**：根据UI设计稿完整展示优质主播活动宣传内容，支持点击跳转至申请页或规则页。

#### 2.2.2 申请页
+ **功能描述**：主播提交优质主播资格申请。
+ **必填项**：
    - 本平台直播录屏（视频上传）
    - WhatsApp Number
    - 其他直播平台信息（平台名称、平台内ID）

#### 2.2.3 优质主播任务奖励页（核心）
+ **功能描述**：展示主播当前及历史周期的任务达成情况、奖励状态，通过服务端统一倒计时确保全球用户时间认知一致。
+ **顶部周期标识与倒计时**：
    - **文案**：`距离本周统计截止还剩：`
    - **数值**：`DD天 HH:MM:SS`
    - **数据来源**：前端**禁止**使用本地时间计算，必须调用后端接口获取剩余秒数或截止时间戳。
    - **交互**：倒计时归零时，仅作为视觉提示，**不触发页面周期切换**。前端应自动刷新请求“本周”数据，此时接口返回的即为上一周期的结算数据。
+ **任务进度展示（按日列表）**：
    - **展示逻辑**：以列表形式展示当前统计周期内每一天的任务达成情况。
    - **列表字段结构**：
        * **统计日期**：`YYYY-MM-DD`
        * **直播总时长**：`实际累计时长 / 要求时长`（如：`5/3`）
        * **高峰时段时长**：`实际累计时长 / 要求时长`（如：`1/2`）
+ **奖励记录（上周/历史周期）**：
    - **展示逻辑**：完全由服务端接口时间决定。只要服务端判定当前时间处于新一周，接口即返回上周的统计结果列表及奖励领取状态。
    - **奖励领取按钮状态**：
        * **待领取**：运营后台审核通过且未领取。
        * **已领取**：显示“已领取”及具体时间。
        * **审核中/未达标**：显示对应状态文案，按钮置灰。

#### 2.2.4 规则介绍页
+ **功能描述**：按照UI设计稿完整展示优质主播活动规则、考核标准、奖励说明等。

## 3. 核心业务规则梳理
### 3.1 有效天与高峰时长判定
+ **有效天**：自然日 `00:00:00` 至 `23:59:59` 时间段内，直播时长累计满 **3小时**。
+ **高峰有效时长**：在配置的“高峰时间段”内，直播时长累计满 **2小时**。

### 3.2 服务端统一倒计时与周期切换逻辑
+ **统一时钟基准**：所有时区用户的“周统计”截止时间统一为 **北京时间每周日 23:59:59**。
+ **倒计时计算**：服务端计算 `截止时间戳 - 当前服务端时间戳`，返回给前端。
+ **前端行为**：
    - 若 `countdown_seconds > 0`：展示“本周”任务进度列表 + 倒计时。
    - 若 `countdown_seconds <= 0`：前端隐藏倒计时，**刷新请求本周数据**。此时接口返回的“本周”数据实际上是上一周（即已结束的周期）的结算数据。
+ **上周数据独立性**：“上周”列表的展示与否，完全取决于服务端接口当前所处的自然周。前端无需通过倒计时归零来触发“上周”数据的加载。

### 3.3 时差处理与防作弊
+ **场景**：用户位于巴西（UTC-3），其本地时间为周日中午，但手动将手机时间调快到周一，试图提前查看奖励。
+ **防御机制**：前端强制读取 `server_timestamp` 进行校准。只要服务端认为还没到周一，前端就不允许展示“上周”的数据或奖励领取按钮。

### 3.4 数据生成时机
+ **周数据**：每周一凌晨统计上一周数据。
+ **日数据**：每天凌晨统计前一天数据。

## 4. 设计角色与环境配置
### 4.1 角色权限
+ **主播**：H5端申请、查看进度、领取奖励。
+ **运营**：管理端配置国家规则、审核申请、审核周数据、查看奖励记录。
+ **系统**：自动统计日/周数据、生成奖励记录、提供统一时间戳接口。

### 4.2 环境配置
+ **时区服务**：后端需部署统一的时区转换服务，所有时间戳均以UTC或北京时间存储，接口返回时明确标注时区。
+ **定时任务**：配置Cron Job，每周一 `00:00`（北京时间）执行周数据聚合任务；每日 `00:00`（北京时间）执行日数据聚合任务。

## 5. 测试场景推演与预期数据
### 5.1 跨时区倒计时一致性
+ **场景**：用户A在北京（UTC+8），用户B在纽约（UTC-5），同时访问H5任务页。
+ **预期**：两人看到的倒计时数值完全一致，且均基于北京时间计算。

### 5.2 周期切换临界点
+ **场景**：当前服务端时间为周日 `23:59:58`，用户保持页面打开。
+ **预期**：2秒后倒计时归零，前端自动刷新，列表数据更新为上周结算数据，倒计时组件隐藏。

### 5.3 本地时间篡改
+ **场景**：用户将手机系统时间手动调快24小时。
+ **预期**：页面仍显示“本周进行中”，倒计时正常，不显示奖励领取按钮。

### 5.4 重新申请逻辑
+ **场景**：主播A审核通过后被置为“失效”，再次提交申请。
+ **预期**：审核列表中生成新的“待审核”记录，原记录保持“失效”状态。
